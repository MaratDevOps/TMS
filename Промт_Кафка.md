# Промт: принципы Kafka-интеграции FI → TRM

```text
Ты проектируешь Kafka-интеграцию SAP FI и Treasury System (TRM) для создания и
обновления заявок на оплату. Используй следующие принципы как обязательные.

## Границы и участники

- SAP FI — источник платёжных потребностей.
- TRM — владелец объекта Payment Request / Заявка на оплату.
- Apache Kafka — транспорт событий между системами.
- Публикация из FI выполняется только через единый компонент
  FI Demand Producer / Outbox. Шесть FI-сущностей не публикуют в Kafka напрямую.
- В TRM событие читает Demand Consumer из consumer group `trm-demand`; затем
  Payment Request Builder создаёт заявку.

## Источники FI

Каждая из сущностей может сформировать одну самостоятельную платёжную потребность:

1. Open Vendor Item (FI-AP) / Открытая позиция кредитора;
2. Open Customer Item (FI-AR) / Открытая позиция дебитора;
3. Taxes / Налоги;
4. Payroll / Зарплата;
5. Contract Payment / Платёж по договору;
6. Manual Request / Ручная заявка.

Для одной FI-потребности создаётся одна Payment Request в TRM (`1 → 1`).
Объединение заявок находится вне ответственности Kafka-события.

## Топики и потоки

- `payment.demand` — основной поток создания платёжных потребностей из FI в TRM;
  число партиций: 4.
- `payment.demand.DLQ` — сообщения основного потока, не обработанные TRM после
  исчерпания retry.
- `payment.status` — отдельный предлагаемый поток изменения статусов из TRM в FI.
  Его event contract должен быть согласован отдельно.
- `payment.status.DLQ` — сообщения статусов, не обработанные FI после исчерпания retry.
- Retry выполняется Consumer. Отдельные retry-топики не использовать, пока это не
  согласовано отдельно.
- Семантика доставки: at-least-once. Consumer обязан обеспечивать идемпотентность.

## Модель контекстной диаграммы

Используй стандартную UML-компонентную нотацию PlantUML:

- `package` — системные границы SAP FI и TRM;
- `component` — прикладные компоненты и шесть FI-сущностей;
- `node` — Apache Kafka Cluster;
- `queue` — Kafka-топики;
- `database` — Payment Request.

Компоновать диаграмму слева направо: `SAP FI → Apache Kafka Cluster → TRM`.
Внутри SAP FI расположить шесть источников в одну горизонтальную линию, ниже —
`FI Demand Producer / Outbox`, ещё ниже — `FI Status Consumer`.
Шесть источников соединяются с Outbox; из Outbox в `payment.demand` идёт одна стрелка.
В Kafka топики располагать вертикально: `payment.demand`, `payment.demand.DLQ`,
`payment.status`, `payment.status.DLQ`.
Внутри TRM располагать вертикально: Demand Consumer, Payment Request Builder,
Payment Request, Status Publisher.
Основной поток: `FI Demand Producer / Outbox → payment.demand → Demand Consumer →
Payment Request Builder → Payment Request`.
Ошибки основного потока направляются: `Demand Consumer → payment.demand.DLQ`.
Обратный поток статусов: `Payment Request → Status Publisher → payment.status →
FI Status Consumer`.
Ошибки статусов направляются: `FI Status Consumer → payment.status.DLQ`.
Для передачи событий используй сплошные стрелки `-->`; пунктирные `..>` допустимы
только для вспомогательных зависимостей, например Schema Registry.

## Маппинг FI-AP → Payment Request

Для Open Vendor Item (FI-AP) применяй следующие правила:

- `Vendor` → `Counterparty`: передаётся технический ID контрагента.
- `Amount` → `Amount`: сумма больше нуля.
- `Currency` → `Currency`: код ISO 4217.
- `Due date` → `Due date`: рассчитанная в FI дата оплаты.
- `BUKRS` → `Company code (BUKRS)`: внутрикорпоративный код компании.
  Не использовать BUKRS как модуль-источник.
- `Origin document` → `Source document`: структура с кодом компании, типом и номером
  документа-основания.
- `Payment purpose` → `Payment purpose`: строковое значение.
- `Payment method` → `Payment method`: код из единого классификатора типов платежа.
- `Payment block` → `Payment block`: boolean, где `true` означает блокировку платежа,
  а `false` — её отсутствие.
- `numberFiPosition` → `Number FI position`: обязательная структура:
  `companyCode (BUKRS)`, `documentType (BLART)`, `documentNumber`,
  `documentData`, `fiscalYear (GJAHR)`, `positionNumber`.

Номер FI-позиции для технической передачи также представляется строкой
`lineItemID`:

FI_POSITION|BUKRS=<COMPANY_CODE>|BLART=<DOCUMENT_TYPE>|
DOCNO=<DOCUMENT_NUMBER>|DOCDATA=<DOCUMENT_DATA>|
GJAHR=<FISCAL_YEAR>|POSNO=<POSITION_NUMBER>

Для прямого поиска FI-документа дополнительно передавай
`accountingDocumentNumber`; его значение совпадает с `numberFiPosition.documentNumber`.

## Идентификация и event contract

Для события FI-AP фиксируй:

- `eventType = payment.demand`;
- `documentType = VENDOR_OPEN_ITEM`;
- `counterpartyRole = VENDOR`;
- `eventId` — UUID записи Outbox, не изменяется при retry;
- `sourceLineItemId` — неизменяемый идентификатор исходной FI-позиции;
- `correlationId` — сквозной идентификатор операции;
- `sourceLineItemReference` — техническая ссылка для открытия FI-позиции.

Kafka key и `sourceLineItemId` формируй как:

FI|role=VENDOR|CP=<VENDOR_ID>|DOCTYPE=VENDOR_OPEN_ITEM|
DOCNO=<ACCOUNTING_DOCUMENT_NUMBER>-<LINE_ITEM_NUMBER>|
BUKRS=<COMPANY_CODE>|GJAHR=<FISCAL_YEAR>

При создании заявки в TRM устанавливай её статус `Created`. Последующие изменения
статуса, отмены и изменения блокировки не включай в `payment.demand`; передавай их
отдельным контрактом `payment.status`.

## Правила качества

- Не создавай заявку при неполном или невалидном обязательном payload.
- TRM дедуплицирует повторные публикации по `eventId`.
- Неизвестные коды классификаторов и ошибки обработки направляй в соответствующий DLQ.
- Не добавляй физические параметры Kafka, правила retention, ACL, TLS/SASL или формат
  сериализации без явных согласованных требований; помечай их как TBD.
- Явно отмечай в документации все несогласованные решения и не выдавай их за факт.
```

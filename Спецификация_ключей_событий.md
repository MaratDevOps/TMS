# Спецификация ключей события `payment.demand`

**Статус:** Черновик 0.1  
**Область действия:** идентификаторы и Kafka key для `payment.demand`  
**Связанные документы:** `Контракт_события_payment.demand.md`,
`Интеграция_Kafka.PlantUml`, `Спецификация_Kafka.md`.

Документ разделяет три независимых идентификатора:

| Идентификатор | Назначение |
|---|---|
| `messageKey` | Kafka key: выбор партиции и порядок сообщений в ней. |
| `eventId` | Идентификатор конкретного экземпляра публикации: идемпотентность и трассировка. |
| `sourceDocumentId` | Уникальный бизнес-идентификатор FI-сущности, породившей потребность. |

---

## 1. Граница применимости

В текущей модели:

- единственный Kafka-продюсер `payment.demand` — **FI**;
- MM и SD — источники документов происхождения (`MIRO`, `Credit Note`), но не Kafka-продюсеры;
- TRM — консьюмер и владелец `Payment Request`, а не Kafka-продюсер этого топика.

Следовательно, правила `messageKey`, `eventId` и `sourceDocumentId` ниже являются
нормативными только для FI-событий. Для MM, SD и TRM зафиксированы правила ссылок на
документы происхождения и допустимость участия в текущем топике.

---

## 2. `messageKey`

### 2.1. Назначение

`messageKey` записывается в key Kafka-сообщения. Kafka вычисляет номер партиции:

```text
partition = hash(messageKey) % 4
```

В топике `payment.demand` четыре партиции. Порядок сообщений гарантирован только
внутри одной партиции и, следовательно, для одного одинакового `messageKey`.

### 2.2. Канонический формат FI

Для всех публикующих FI-сущностей применяется строка UTF-8 в следующем формате:

```text
FI|role=<COUNTERPARTY_ROLE>|CP=<COUNTERPARTY_ID>|DOCTYPE=<DOCUMENT_TYPE>|
DOCNO=<DOCUMENT_NUMBER>|BUKRS=<COMPANY_CODE>|GJAHR=<FISCAL_YEAR>
```

Пробелы, переносы строк и неэкранированные символы-разделители `|` и `=` в значениях
не допускаются. Если исходное значение содержит такой символ, правило экранирования
должно быть утверждено до реализации.

| Компонент | Обяз. | Правило |
|---|---:|---|
| `FI` | Да | Фиксированный код модуля-публикатора. |
| `role` | Да | Роль контрагента. Минимально: `VENDOR` или `CUSTOMER`. |
| `CP` | Да | Технический ID контрагента / Business Partner, не отображаемое имя. |
| `DOCTYPE` | Да | Тип публикующей FI-сущности из раздела 2.3. |
| `DOCNO` | Да | Идентификатор FI-позиции, FI-документа или реестра. |
| `BUKRS` | Да | Код компании FI. |
| `GJAHR` | Да | Финансовый год FI. |

### 2.3. Допустимые `DOCTYPE`

| Значение | FI-сущность |
|---|---|
| `VENDOR_OPEN_ITEM` | Open Vendor Item (FI-AP) / Открытая позиция кредитора |
| `CUSTOMER_OPEN_ITEM` | Open Customer Item (FI-AR) / Открытая позиция дебитора |
| `TAX` | Taxes / Налоги |
| `PAYROLL` | Payroll / Зарплата |
| `CONTRACT_PAYMENT` | Contract Payment / Платёж по договору |
| `MANUAL_REQUEST` | Manual Request / Ручная заявка |

Для `TAX`, `PAYROLL`, `CONTRACT_PAYMENT` и `MANUAL_REQUEST` необходимо отдельно
подтвердить, какой именно FI-идентификатор используется как `DOCNO`; до этого
публикация соответствующих типов не считается специфицированной для реализации.

### 2.4. Примеры `messageKey`

```text
FI|role=VENDOR|CP=0001007788|DOCTYPE=VENDOR_OPEN_ITEM|DOCNO=1900012345|BUKRS=1000|GJAHR=2026
FI|role=CUSTOMER|CP=0002003344|DOCTYPE=CUSTOMER_OPEN_ITEM|DOCNO=1800012345|BUKRS=1000|GJAHR=2026
```

## 3. `sourceDocumentId`

### 3.1. Назначение

`sourceDocumentId` идентифицирует бизнес-сущность в FI, по которой возникла платёжная
потребность. Он применяется для трассировки между FI, Outbox, Kafka и `Payment Request`.

### 3.2. Правило текущей версии

В текущей версии `sourceDocumentId` **равен** каноническому `messageKey`.

Такое правило обеспечивает:

- однозначную связь одного FI-источника с одной заявкой;
- отсутствие коллизий между поставщиком и покупателем с одинаковыми номерами документов;
- воспроизводимую трассировку в системах-участниках.

Пример:

```text
sourceDocumentId =
FI|role=VENDOR|CP=0001007788|DOCTYPE=VENDOR_OPEN_ITEM|DOCNO=1900012345|BUKRS=1000|GJAHR=2026
```

Если в будущем потребуется изменить формат Kafka key для перераспределения партиций,
`sourceDocumentId` должен сохранить неизменяемую бизнес-идентичность FI-сущности.
Это изменение требует новой версии контракта.

## 4. `eventId`

### 4.1. Назначение

`eventId` идентифицирует конкретную запись Outbox и конкретный экземпляр публикации
в Kafka. Он не является Kafka key и не заменяет `sourceDocumentId`.

### 4.2. Правило

Для текущей версии требуется UUID, созданный в момент записи события в Outbox:

```text
eventId = UUID
```

`eventId`:

- обязателен в payload;
- не изменяется при retry одной и той же записи Outbox;
- передаётся в DLQ без изменения;
- используется TRM Consumer для дедупликации обработанных экземпляров.

Формат UUID (v4 или v7) требует окончательного выбора владельцем интеграции до создания
физической Avro/JSON Schema. До выбора UUID-версии строковое представление UUID является
обязательным, а конкретная версия остаётся **TBD**.

## 5. Правила для MM, SD, FI и TRM

### 5.1. MM — Procurement / Закупки

| Аспект | Правило |
|---|---|
| Kafka-продюсер `payment.demand` | Нет |
| Документ происхождения | Vendor Invoice (MIRO) / Счёт поставщика |
| Публикующая FI-сущность | `VENDOR_OPEN_ITEM` |
| Представление в событии | Блок `originDocument`; не входит в `messageKey` и `sourceDocumentId`. |

Идентификатор происхождения рекомендуется хранить отдельно:

```text
originDocumentId = MM|DOCTYPE=MIRO|DOCNO=<MIRO_DOCUMENT_NUMBER>|BUKRS=<COMPANY_CODE>|GJAHR=<FISCAL_YEAR>
```

Точные технические поля MIRO, из которых формируется этот идентификатор, должны быть
подтверждены владельцем SAP FI/MM до реализации.

### 5.2. SD — Sales and Distribution / Сбыт

| Аспект | Правило |
|---|---|
| Kafka-продюсер `payment.demand` | Нет |
| Документ происхождения | Credit Note / Кредит-нота |
| Публикующая FI-сущность | `CUSTOMER_OPEN_ITEM` |
| Представление в событии | Блок `originDocument`; не входит в `messageKey` и `sourceDocumentId`. |

Идентификатор происхождения рекомендуется хранить отдельно:

```text
originDocumentId = SD|DOCTYPE=CREDIT_NOTE|DOCNO=<CREDIT_NOTE_NUMBER>
```

Полный набор технических полей Credit Note требует подтверждения владельцем SAP SD/FI.

### 5.3. FI — Financial Accounting / Финансовый учёт

| Аспект | Правило |
|---|---|
| Kafka-продюсер `payment.demand` | Да |
| `messageKey` | Канонический формат из раздела 2.2 |
| `sourceDocumentId` | Равен `messageKey` |
| `eventId` | UUID записи Outbox |
| Документы происхождения | Передаются отдельно, если FI-сущность создана из MIRO или Credit Note |

### 5.4. TRM — Treasury System / Казначейская система

| Аспект | Правило |
|---|---|
| Kafka-продюсер `payment.demand` | Нет |
| Роль в текущем топике | Consumer и владелец `Payment Request` |
| `messageKey`, `eventId`, `sourceDocumentId` для публикации | Не применяются |

Если TRM потребуется публиковать собственные события в будущем, для них должен быть
определён отдельный event contract и отдельные правила ключей. Правила этого документа
на такие события не распространяются.

## 6. Проверки и ошибки

| Проверка | Действие при нарушении |
|---|---|
| `messageKey` не соответствует формату FI | Не публиковать; зафиксировать ошибку Outbox/Publisher. |
| `DOCTYPE` не входит в утверждённый список | Не публиковать; направить на разбор. |
| Нет `BUKRS` или `GJAHR` | Не публиковать FI-событие. |
| Нет `eventId` | Не публиковать событие. |
| Повторный `eventId` у Consumer | Не создавать дубликат `Payment Request`. |
| `originDocumentId` не может быть сформирован | Не блокировать FI-событие, если документ происхождения не обязателен для данного типа; зафиксировать отсутствие происхождения. |

---

## 7. Открытые решения

1. UUID v4 или UUID v7 для `eventId`.
2. Точные поля SAP для `originDocumentId` MIRO и Credit Note.
3. Допустимые роли контрагентов для налогов, зарплаты, договорных и ручных платежей.
4. Правила `DOCNO` для `TAX`, `PAYROLL`, `CONTRACT_PAYMENT` и `MANUAL_REQUEST`.
5. Правило экранирования значений, содержащих `|` или `=`.
6. Нужна ли отдельная неизменяемая версия `sourceDocumentId`, если Kafka key будет изменён.

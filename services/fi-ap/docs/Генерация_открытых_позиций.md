# Генерация открытых позиций кредиторов

## 1. Назначение

Документ описывает механизм массового создания тестовых открытых позиций кредиторов
в микросервисе FI-AP.

Генератор должен:

- создавать заданное количество уникальных `OpenVendorItem`;
- выполнять генерацию в заданном количестве параллельных потоков;
- заполнять все обязательные реквизиты позиции;
- создавать для каждой позиции событие `Outbox`;
- сохранять `OpenVendorItem` и `Outbox` в одной транзакции;
- обеспечивать воспроизводимость запуска при использовании одинакового сценария.

Генератор имитирует источник платёжных потребностей и не воспроизводит бухгалтерскую
логику SAP FI-AP.

Технологический стек и компоненты приложения описаны в документе
[`Техническая_архитектура_FI_AP.md`](Техническая_архитектура_FI_AP.md).

## 2. Сценарий генерации

Сценарий — именованный набор параметров одного запуска генератора. Несколько сценариев
хранятся в одном конфигурационном YAML-файле. При запуске выбирается один из них.

Минимальная конфигурация:

```yaml
generation:
  activeScenario: smoke

  referenceData:
    companyCodes: ["1000"]
    counterpartyIds: ["0001007788"]
    currencies: ["RUB"]
    paymentMethods: ["BANK_TRANSFER"]
    statuses: ["CREATED"]
    originDocumentTypes: ["MIRO"]

  scenarios:
    smoke:
      positionCount: 10
      parallelThreads: 1
      randomSeed: 1001
      positionsPerDocument: 10
      baseDocumentDate: 2026-01-01
      originDocumentShare: 1.0
      amount:
        min: 100.00
        max: 1000000.00
      dueDays:
        min: 1
        max: 30
      paymentBlockProbability: 0.05
      paymentPurposeTemplate: "Оплата по FI-позиции %s"
      stopOnError: true

    parallel-load:
      positionCount: 10000
      parallelThreads: 8
      randomSeed: 2001
      positionsPerDocument: 10
      baseDocumentDate: 2026-01-01
      originDocumentShare: 0.8
      amount:
        min: 100.00
        max: 1000000.00
      dueDays:
        min: 1
        max: 30
      paymentBlockProbability: 0.05
      paymentPurposeTemplate: "Оплата по FI-позиции %s"
      stopOnError: false
```

### 2.1. Параметры сценария

| Параметр | Тип | Обязательность | Описание |
|---|---|---|---|
| `positionCount` | integer | Обязательный | Общее количество заданий на создание позиций. При отсутствии ошибок совпадает с количеством успешно сохранённых позиций. |
| `parallelThreads` | integer | Обязательный | Размер фиксированного пула потоков, одновременно выполняющих генерацию и сохранение позиций. |
| `randomSeed` | integer | Обязательный | Начальное значение генератора тестовых данных. Одинаковые сценарий и `randomSeed` должны формировать одинаковые бизнес-данные независимо от порядка выполнения потоков. |
| `positionsPerDocument` | integer | Обязательный | Количество позиций, создаваемых для одного исходного FI-документа. Допустимый диапазон — от `1` до `999`. |
| `baseDocumentDate` | date | Обязательный | Начальная дата для детерминированного формирования `documentData`. |
| `originDocumentShare` | decimal | Обязательный | Доля позиций с документом-основанием: от `0.0` до `1.0`. Значение `0.8` означает, что документ-основание создаётся примерно для 80 % позиций. |
| `amount.min` | decimal | Обязательный | Минимальная генерируемая сумма, строго больше нуля. |
| `amount.max` | decimal | Обязательный | Максимальная генерируемая сумма, не меньше `amount.min`. |
| `dueDays.min` | integer | Обязательный | Минимальное количество дней от `documentData` до `dueDate`. |
| `dueDays.max` | integer | Обязательный | Максимальное количество дней от `documentData` до `dueDate`. |
| `paymentBlockProbability` | decimal | Обязательный | Вероятность установки блокировки платежа: от `0.0` до `1.0`. |
| `paymentPurposeTemplate` | string | Обязательный | Шаблон назначения платежа. `%s` заменяется на сформированный `lineItemID`. |
| `stopOnError` | boolean | Обязательный | `true` — остановить выдачу новых заданий после первой ошибки; `false` — продолжить обработку остальных позиций и зафиксировать ошибку в результате запуска. |

### 2.2. Выбор сценария

Сценарий выбирается одним из следующих способов:

1. параметром командной строки:

   ```text
   fi-ap-generator --scenario parallel-load
   ```


2. значением `generation.activeScenario` в YAML-файле.

Приоритет выбора:

```text
параметр командной строки
→ generation.activeScenario
```

Если выбранное имя отсутствует в `generation.scenarios`, запуск не начинается.

### 2.3. Валидация настроек

Перед началом генерации сервис проверяет:

- `positionCount >= 1`;
- `parallelThreads >= 1`;
- `parallelThreads <= positionCount`;
- `positionsPerDocument` находится в диапазоне от `1` до `999`;
- `originDocumentShare` находится в диапазоне от `0.0` до `1.0`;
- `amount.min > 0` и `amount.max >= amount.min`;
- `dueDays.min >= 0` и `dueDays.max >= dueDays.min`;
- `paymentBlockProbability` находится в диапазоне от `0.0` до `1.0`;
- списки в `referenceData` не пусты;
- имя выбранного сценария существует;
- все обязательные параметры сценария заполнены.

Ошибка конфигурации завершает запуск до создания записей в базе данных.

## 3. Обязательные реквизиты OpenVendorItem

| Реквизит | Правило генерации |
|---|---|
| `id` | Новый UUID. Используется как первичный ключ `OpenVendorItem`. |
| `sourceLineItemId` | Уникальный составной идентификатор позиции. Одновременно используется как Kafka key. |
| `documentType` | Фиксированное значение `VENDOR_OPEN_ITEM`. |
| `companyCode` | Код компании из настроенного набора тестовых значений, например `1000`. |
| `fiscalYear` | Год из `documentData`. Формат `YYYY`. |
| `documentNumber` | Уникальный номер исходного FI-документа, полученный из PostgreSQL sequence `fi_document_number_seq`. |
| `documentData` | Дата исходного FI-документа, детерминированно сформированная относительно `baseDocumentDate`. |
| `positionNumber` | Порядковый номер позиции внутри исходного FI-документа, дополненный слева нулями до трёх знаков. |
| `lineItemID` | Канонический строковый идентификатор FI-позиции. |
| `sourceLineItemReference` | Техническая ссылка на позицию в сервисе FI-AP. |
| `counterpartyId` | Идентификатор кредитора из набора тестовых контрагентов. |
| `counterpartyRole` | Фиксированное значение `VENDOR`. |
| `amount` | Положительное десятичное число. Значение должно быть строго больше нуля. |
| `currency` | Трёхбуквенный код ISO 4217, например `RUB`. |
| `dueDate` | Плановая дата оплаты, не раньше `documentData`. |
| `paymentPurpose` | Текстовое назначение платежа, содержащее номер генерируемой позиции. |
| `paymentMethod` | Код способа оплаты из настроенного набора тестовых значений. |
| `paymentBlock` | Булево значение признака блокировки платежа. |
| `status` | Код статуса из настроенного набора тестовых значений. |

`originDocumentId` не является обязательным. Наличие документа-основания определяется
параметром `originDocumentShare`.

### 3.1. Формирование номера исходного документа

Параметр начального номера документа в сценарии не используется. Уникальный
`documentNumber` выдаётся PostgreSQL:

```sql
nextval('fi_document_number_seq')
```

Количество необходимых исходных документов рассчитывается до запуска потоков:

```text
documentCount = ceil(positionCount / positionsPerDocument)
```

Для каждого нового исходного документа генератор один раз получает значение sequence.
Полученный `documentNumber` назначается максимум `positionsPerDocument` позициям.

Для задания с номером `N`:

```text
documentIndex = floor((N - 1) / positionsPerDocument)
positionNumber = ((N - 1) % positionsPerDocument) + 1
```

Позиция получает `documentNumber` документа с вычисленным `documentIndex`.
`positionNumber` представляется строкой из трёх знаков, например `001`.

Sequence обеспечивает уникальность номеров при параллельной работе потоков и
нескольких экземпляров сервиса. Пропуски в последовательности после отката транзакции
допустимы. Поиск `MAX(documentNumber) + 1` не используется.

## 4. Формирование идентификаторов

### 4.1. sourceLineItemId

`sourceLineItemId` формируется по правилу контракта `payment.demand`:

```text
FI|role=VENDOR|CP=<VENDOR_ID>|DOCTYPE=VENDOR_OPEN_ITEM|
DOCNO=<DOCUMENT_NUMBER>-<POSITION_NUMBER>|
BUKRS=<COMPANY_CODE>|GJAHR=<FISCAL_YEAR>
```

Пример:

```text
FI|role=VENDOR|CP=0001007788|DOCTYPE=VENDOR_OPEN_ITEM|
DOCNO=1900012345-001|BUKRS=1000|GJAHR=2026
```

### 4.2. lineItemID

`lineItemID` формируется из реквизитов позиции:

```text
FI_POSITION|BUKRS=<COMPANY_CODE>|DOCTYPE=VENDOR_OPEN_ITEM|
DOCNO=<DOCUMENT_NUMBER>|DOCDATA=<DOCUMENT_DATA>|
GJAHR=<FISCAL_YEAR>|POSNO=<POSITION_NUMBER>
```

Пример:

```text
FI_POSITION|BUKRS=1000|DOCTYPE=VENDOR_OPEN_ITEM|
DOCNO=1900012345|DOCDATA=2026-08-12|GJAHR=2026|POSNO=001
```

### 4.3. sourceLineItemReference

Для тестового сервиса используется внутренняя техническая ссылка:

```text
fi-ap://open-vendor-items/<OpenVendorItem.id>
```

Пример:

```text
fi-ap://open-vendor-items/4eb35ed1-3422-4ed4-b1f8-d405ea2838cb
```

### 4.4. documentKey

`documentKey` не хранится как реквизит `OpenVendorItem`. Он формируется при подготовке
`payload` события `payment.demand` из реквизитов исходного документа:

```text
DOCUMENT|BUKRS=<COMPANY_CODE>|DOCTYPE=<DOCUMENT_TYPE>|
DOCNO=<DOCUMENT_NUMBER>|DOCDATA=<DOCUMENT_DATA>
```

## 5. Документ-основание

Для выбранной доли позиций генератор создаёт `OriginDocument` до формирования
`OpenVendorItem`.

Обязательные реквизиты `OriginDocument`:

| Реквизит | Правило генерации |
|---|---|
| `id` | Новый UUID, первичный ключ документа-основания. |
| `companyCode` | Код компании; должен совпадать с `OpenVendorItem.companyCode`. |
| `documentType` | Тип тестового документа-основания, например `MIRO`. |
| `documentNumber` | Уникальный номер тестового документа-основания. |
| `documentData` | Дата документа-основания, не позднее `OpenVendorItem.documentData`. |

Созданный `OriginDocument.id` записывается в `OpenVendorItem.originDocumentId`.
Если документ-основание для позиции не генерируется, `originDocumentId` остаётся
пустым.

## 6. Механизм параллельной генерации

Генерация выполняется фиксированным пулом размером `parallelThreads`.

Перед началом работы сервис формирует диапазон последовательных номеров:

```text
1..positionCount
```

До передачи заданий потокам сервис получает из `fi_document_number_seq` значения для
`documentCount` исходных документов и сопоставляет задания документам и позициям.
Это исключает зависимость назначения номеров документов от порядка выполнения
потоков.

Каждый номер задания выдаётся только одному потоку. Вместе с ним передаются заранее
назначенные `documentNumber` и `positionNumber`.

Для каждого номера поток последовательно:

1. вычисляет локальное начальное значение случайных данных из `randomSeed` и номера
   позиции;
2. генерирует обязательные реквизиты `OpenVendorItem`;
3. при необходимости генерирует `OriginDocument`;
4. формирует `sourceLineItemId`, `lineItemID` и `sourceLineItemReference`;
5. проверяет обязательность, форматы и уникальность реквизитов;
6. формирует событие `payment.demand`;
7. открывает транзакцию базы данных;
8. сохраняет `OriginDocument`, если он был сформирован;
9. сохраняет `OpenVendorItem`;
10. сохраняет связанную запись `Outbox`;
11. завершает транзакцию;
12. фиксирует результат обработки позиции в журнале.

Процесс представлен отдельно на диаграмме
[`Схема_генерации_открытых_позиций.PlantUml`](Схема_генерации_открытых_позиций.PlantUml).

Количество потоков определяет максимальное число одновременно обрабатываемых
позиций, но не изменяет `positionCount`.

## 7. Транзакционные гарантии

Одна позиция обрабатывается в отдельной транзакции:

```text
OriginDocument (если нужен)
+ OpenVendorItem
+ Outbox
```

Транзакция либо сохраняет все связанные записи, либо не сохраняет ни одной.
Публикация в Kafka не входит в эту транзакцию и выполняется обработчиком Outbox после
её успешного завершения.

Сбой одной позиции не должен откатывать ранее сохранённые позиции.

## 8. Обработка ошибок

Если `stopOnError: false`:

- ошибка фиксируется с номером позиции и причиной;
- транзакция ошибочной позиции откатывается;
- поток получает следующий номер;
- остальные потоки продолжают работу.

Если `stopOnError: true`:

- сервис прекращает выдавать потокам новые номера;
- уже начатые транзакции завершаются штатно;
- сервис ожидает завершения всех потоков;
- запуск завершается с ошибкой.

Автоматически увеличивать количество попыток создания позиции нельзя: это может
привести к превышению `positionCount`. Повтор должен использовать тот же номер
задания и те же сгенерированные бизнес-данные.

## 9. Повторный запуск

Каждый запуск создаёт новый набор открытых позиций. Существующие `OriginDocument`,
`OpenVendorItem` и `Outbox` не удаляются и не обновляются.

Для нового запуска:

- создаётся новый `runId`;
- из `fi_document_number_seq` получаются новые номера документов;
- генерируются новые технические UUID;
- создаются новые `sourceLineItemId`, `lineItemID` и `documentKey`;
- данные предыдущих запусков сохраняются без изменений.

Повторный запуск одного сценария не является повторной публикацией ранее созданных
событий и не используется для проверки upsert или дедупликации. Такие проверки
должны запускаться отдельными специализированными операциями.

## 10. Воспроизводимость

Генерируемые значения сумм, дат, признака блокировки и выбор значений из
`referenceData` должны зависеть от:

```text
randomSeed + последовательный номер позиции
```

Они не должны зависеть от номера потока или порядка планирования потоков. Благодаря
этому в рамках запуска одинаковым заданиям соответствуют одинаковые генерируемые
значения при любом допустимом `parallelThreads`.

При повторном запуске `documentNumber` заново получается из
`fi_document_number_seq`. Поэтому `documentNumber`, `sourceLineItemId`, `lineItemID`,
`documentKey` и технические UUID не воспроизводятся и не конфликтуют с предыдущим
набором. `randomSeed` обеспечивает воспроизводимость остальных тестовых данных.

## 11. Жизненный цикл и завершение запуска

Приложение работает как одноразовый CLI-процесс:

1. создаёт `runId`;
2. получает имя сценария через `--scenario` либо из `generation.activeScenario`;
3. загружает и проверяет конфигурацию;
4. проверяет доступность PostgreSQL и Kafka;
5. запускает обработчик Outbox;
6. запускает параллельную генерацию позиций;
7. ожидает завершения всех генераторов;
8. ожидает результата публикации всех событий текущего запуска;
9. формирует итоговую статистику;
10. завершает процесс с соответствующим кодом.

События текущего запуска определяются по набору созданных `Outbox.eventId`, который
координатор хранит до завершения процесса.

Итоговая статистика содержит:

- имя сценария;
- `runId`;
- запрошенное количество позиций;
- количество успешно созданных позиций;
- количество ошибок генерации;
- количество опубликованных событий;
- количество событий с ошибкой публикации;
- фактически использованное число потоков;
- время начала и окончания;
- общую длительность;
- среднюю скорость создания позиций.

Процесс завершается только после того, как все события текущего запуска опубликованы
либо получили окончательную ошибку согласно политике повторов Outbox.

### 11.1. Формат итогового результата

Итоговый результат формируется как один YAML-документ и выводится в `stdout`.
Структурированные диагностические логи выводятся отдельно в `stderr` в формате JSON.
Смешивание логов и YAML-результата в одном потоке запрещено.

Технические имена полей результата:

| Поле | Тип | Описание |
|---|---|---|
| `resultVersion` | string | Версия структуры итогового результата. Начальное значение — `1.0`. |
| `runId` | UUID string | Уникальный идентификатор запуска, создаваемый до загрузки конфигурации. |
| `scenario` | string или null | Имя выбранного сценария. `null`, если его не удалось определить. |
| `status` | string | Итоговый статус: `COMPLETED`, `COMPLETED_WITH_ERRORS`, `INTERRUPTED` или `FAILED`. |
| `requestedPositions` | integer | Количество заданий на создание позиций из сценария. |
| `createdPositions` | integer | Количество успешно сохранённых `OpenVendorItem`. |
| `generationErrors` | integer | Количество заданий, завершившихся ошибкой генерации или сохранения. |
| `publishedEvents` | integer | Количество событий текущего запуска со статусом доставки `PUBLISHED`. |
| `publicationErrors` | integer | Количество событий текущего запуска с окончательной ошибкой публикации. Ошибки промежуточных попыток сюда не входят. |
| `parallelThreads` | integer | Фактическое количество goroutine генератора. |
| `startedAt` | datetime string | Время начала процесса в UTC в формате RFC 3339. |
| `finishedAt` | datetime string | Время формирования итогового результата в UTC в формате RFC 3339. |
| `durationMs` | integer | Полная длительность процесса в миллисекундах. |
| `generationDurationMs` | integer | Длительность этапа генерации позиций в миллисекундах. |
| `positionsPerSecond` | decimal | `createdPositions / generationDurationMs * 1000`. |
| `errorCodes` | array of string | Машинные коды категорий ошибок. Для успешного запуска — пустой массив. |
| `exitCode` | integer | Код завершения процесса из раздела 11.2. |

Пример:

```yaml
resultVersion: "1.0"
runId: "7a8742c7-8d7c-4ab3-8431-a86f251417db"
scenario: "parallel-load"
status: "COMPLETED"
requestedPositions: 10000
createdPositions: 10000
generationErrors: 0
publishedEvents: 10000
publicationErrors: 0
parallelThreads: 8
startedAt: "2026-08-31T15:00:00Z"
finishedAt: "2026-08-31T15:01:15Z"
```

Допустимые элементы `errorCodes`:

- `CONFIGURATION_ERROR`;
- `DEPENDENCY_UNAVAILABLE`;
- `GENERATION_ERROR`;
- `PUBLICATION_ERROR`;
- `INTERRUPTED`.

Правила стабильности:

- имена полей и их смысл не изменяются в пределах одной `resultVersion`;
- удаление, переименование или изменение типа поля требует новой версии результата;
- новые необязательные поля могут добавляться только с сохранением обратной
  совместимости;
- даты всегда передаются в UTC по RFC 3339;
- числовые значения не форматируются локализованными разделителями;
- подробности отдельных ошибок передаются через JSON-логи, а не в YAML-результате.

Если конфигурация не загружена, результат всё равно содержит все перечисленные поля.
Неизвестные числовые значения заполняются нулями, `scenario` — значением `null`.

### 11.2. Коды завершения

| Код | Значение |
|---:|---|
| `0` | Все запрошенные позиции созданы, а соответствующие события опубликованы. |
| `1` | Возникли ошибки генерации или публикации. |
| `2` | Конфигурация отсутствует либо не прошла валидацию. |
| `3` | При запуске недоступны PostgreSQL или Kafka. |

### 11.3. Прерывание пользователем

При получении `Ctrl+C` или сигнала завершения приложение:

1. прекращает выдавать генераторам новые задания;
2. отменяет ещё не начатые задания;
3. позволяет завершить или корректно откатить активные транзакции;
4. прекращает брать новые события Outbox в обработку;
5. завершает активные попытки публикации;
6. формирует итоговую статистику по фактически обработанным данным;
7. завершается с кодом `1`.

## 12. Критерии приёмки

1. При корректном сценарии создаётся ровно `positionCount` успешных позиций, если
   отсутствуют ошибки базы данных.
2. Каждая созданная позиция имеет все обязательные реквизиты.
3. `sourceLineItemId` и `lineItemID` уникальны.
4. Каждой позиции соответствует запись `Outbox`, созданная в той же транзакции.
5. Число одновременно работающих потоков не превышает `parallelThreads`.
6. Повторный запуск с теми же `randomSeed` и параметрами воспроизводит тестовые
   значения, кроме номеров документов, производных идентификаторов и UUID.
7. Ошибка отдельной позиции не создаёт неполные связанные данные.
8. Повторный запуск добавляет новый набор и не изменяет данные предыдущих запусков.
9. Успешный процесс завершается только после публикации всех событий текущего запуска.

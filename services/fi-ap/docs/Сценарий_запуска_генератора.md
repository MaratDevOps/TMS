# Сценарий запуска генератора открытых позиций

## 1. Назначение

Документ описывает сценарий использования одноразового CLI-генератора FI-AP:
запуск, основной поток, альтернативные исходы и критерии успешного завершения.

Правила генерации, параметры сценариев и формат результата определены в
[`Генерация_открытых_позиций.md`](Генерация_открытых_позиций.md).
Порядок шагов представлен на диаграмме активности
[`Схема_генерации_открытых_позиций.PlantUml`](Схема_генерации_открытых_позиций.PlantUml).

## 2. Сценарий использования

| Элемент | Значение |
|---|---|
| Название | Запуск генерации открытых позиций кредиторов |
| Идентификатор | UC-FI-AP-GEN-01 |
| Актор | Инженер, оператор тестового стенда или CI-процесс |
| Цель | Создать заданное количество тестовых `OpenVendorItem`, подготовить события `payment.demand` в Outbox и дождаться результата публикации |
| Уровень | Пользовательский сценарий CLI |
| Область | Микросервис FI-AP |

## 3. Предусловия

1. Доступен исполняемый модуль `fi-ap-generator` либо исходный код для запуска через `go run`.
2. Существует YAML-конфигурация с валидными секциями `postgres`, `kafka`, `generation` и `outboxPublisher`.
3. В конфигурации определён выбранный сценарий через `--scenario` либо `generation.activeScenario`.
4. PostgreSQL доступен по `postgres.dsn`.
5. Kafka доступна по адресам из `kafka.brokers`, если запуск должен завершиться успешной публикацией.

## 4. Триггер

Актор запускает генератор:

```text
go run ./cmd/fi-ap-generator --config configs/generation.yaml --scenario smoke
```

Либо:

```text
fi-ap-generator --config configs/generation.yaml --scenario parallel-load
```

Если `--scenario` не указан, используется `generation.activeScenario`.

## 5. Основной успешный поток

1. Процесс создаёт `runId` и фиксирует время начала.
2. Загружает YAML-конфигурацию и выбирает сценарий.
3. Проверяет параметры сценария и справочные данные.
4. Проверяет доступность PostgreSQL и Kafka.
5. Применяет миграции схемы при необходимости.
6. Запускает обработчик Outbox.
7. Рассчитывает `documentCount` и получает номера документов через `fi_document_number_seq`.
8. Формирует задания `1..positionCount` и назначает каждому `documentNumber` и `positionNumber`.
9. Запускает пул из `parallelThreads` потоков генерации.
10. Каждый поток генерирует позицию, формирует `payment.demand` и в одной транзакции сохраняет `OriginDocument` при необходимости, `OpenVendorItem` и `Outbox`.
11. Процесс ожидает завершения всех генераторов.
12. Процесс ожидает публикации всех событий текущего запуска либо окончательной ошибки публикации.
13. Формирует итоговый YAML-результат и выводит его в `stdout`.
14. Завершается с кодом `0`.

## 6. Альтернативные потоки

### 6.1. Ошибка конфигурации

На шагах 2–3 конфигурация отсутствует, не читается или не проходит валидацию.

- записи в базе данных не создаются;
- в `stdout` выводится YAML-результат со статусом `FAILED` и `CONFIGURATION_ERROR`;
- процесс завершается с кодом `2`.

### 6.2. Недоступны зависимости

На шаге 4 PostgreSQL или Kafka недоступны.

- генерация не начинается;
- в `stdout` выводится YAML-результат со статусом `FAILED` и `DEPENDENCY_UNAVAILABLE`;
- процесс завершается с кодом `3`.

### 6.3. Ошибки генерации при `stopOnError: false`

На шаге 10 отдельные задания завершаются ошибкой сохранения или валидации.

- транзакция ошибочного задания откатывается;
- остальные задания продолжают обработку;
- итоговый статус — `COMPLETED_WITH_ERRORS`;
- процесс завершается с кодом `1`.

### 6.4. Ошибки генерации при `stopOnError: true`

После первой ошибки генерации:

- выдача новых заданий прекращается;
- уже начатые транзакции завершаются или откатываются;
- итоговый статус — `COMPLETED_WITH_ERRORS` либо `FAILED`;
- процесс завершается с кодом `1`.

### 6.5. Ошибки публикации

Генерация завершена, но часть событий текущего запуска получила окончательную ошибку публикации.

- позиции и записи Outbox сохранены;
- `publicationErrors > 0`;
- итоговый статус — `COMPLETED_WITH_ERRORS`;
- процесс завершается с кодом `1`.

### 6.6. Прерывание пользователем

Актор отправляет `Ctrl+C` или `SIGTERM`.

1. Прекращается выдача новых заданий генерации.
2. Отменяются ещё не начатые задания.
3. Активные транзакции завершаются или корректно откатываются.
4. Обработчик Outbox прекращает захват новых событий.
5. Активные попытки публикации завершаются в пределах `shutdownTimeout`.
6. Формируется YAML-итог по фактически обработанным данным.
7. Процесс завершается со статусом `INTERRUPTED` и кодом `1`.

## 7. Постусловия

После успешного завершения:

- создано `positionCount` открытых позиций, если не было ошибок генерации;
- каждой созданной позиции соответствует запись `Outbox`, сохранённая в той же транзакции;
- события текущего запуска опубликованы либо получили окончательный статус ошибки публикации;
- в `stdout` выведен один YAML-документ результата;
- в `stderr` выведены JSON-логи без смешивания с итоговым результатом.

После любого завершения:

- данные предыдущих запусков не удаляются и не обновляются;
- повторный запуск создаёт новый набор позиций с новыми номерами документов.

## 8. Результат для актора

Актор получает:

- YAML-результат в `stdout` со стабильными техническими именами полей;
- диагностические JSON-логи в `stderr`;
- код завершения процесса:

| Код | Значение |
|---:|---|
| `0` | Все запрошенные позиции созданы, соответствующие события опубликованы |
| `1` | Ошибки генерации, публикации или прерывание |
| `2` | Ошибка конфигурации |
| `3` | Недоступны PostgreSQL или Kafka |

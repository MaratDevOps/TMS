# Алгоритм обработчика Outbox

## 1. Назначение

Обработчик Outbox публикует подготовленные события `payment.demand` в Kafka и
сохраняет историю каждой попытки в `outbox_delivery_attempts`.

Обработчик работает независимо от транзакции создания `open_vendor_items` и
`outbox`. Запись `outbox` после создания не изменяется.

Визуальное представление алгоритма вынесено в
[`Схема_обработчика_Outbox.PlantUml`](Схема_обработчика_Outbox.PlantUml).

## 2. Гарантия доставки

Используется модель **at-least-once**:

- событие не теряется после сохранения в `outbox`;
- до подтверждения успешной публикации событие может отправляться повторно;
- при сбое между подтверждением Kafka и фиксацией `PUBLISHED` возможен дубль;
- все повторы используют прежний `event_id`;
- потребитель выполняет дедупликацию по `event_id`.

Exactly-once между PostgreSQL и Kafka не гарантируется, поскольку они не участвуют
в общей распределённой транзакции.

## 3. Конфигурация

Параметры обработчика задаются в YAML независимо от сценария генерации:

```yaml
outboxPublisher:
  enabled: true
  workers: 8
  batchSize: 100
  pollInterval: 500ms
  claimTransactionTimeout: 5s
  lockTimeout: 30s
  kafkaSendTimeout: 10s
  maxAttempts: 5
  retry:
    initialInterval: 1s
    multiplier: 2.0
    maxInterval: 60s
    jitter: 0.20
  shutdownTimeout: 30s
```

| Параметр | Назначение |
|---|---|
| `enabled` | Включает обработчик Outbox. Для штатного запуска FI-AP должно быть `true`. |
| `workers` | Максимальное количество событий, одновременно отправляемых в Kafka. |
| `batchSize` | Максимальное количество событий, захватываемых за одну транзакцию выборки. |
| `pollInterval` | Пауза перед повторной проверкой Outbox, если подходящие события не найдены. |
| `claimTransactionTimeout` | Максимальная длительность транзакции выборки и создания попыток. |
| `lockTimeout` | Период владения событием экземпляром обработчика. |
| `kafkaSendTimeout` | Максимальное ожидание подтверждения Kafka для одной отправки. |
| `maxAttempts` | Максимальное количество попыток публикации одного события. |
| `retry.initialInterval` | Начальная задержка перед повторной попыткой. |
| `retry.multiplier` | Множитель экспоненциального увеличения задержки. |
| `retry.maxInterval` | Верхняя граница задержки. |
| `retry.jitter` | Случайное отклонение задержки, предотвращающее одновременные повторы. |
| `shutdownTimeout` | Максимальное время штатного завершения активных отправок. |

При запуске проверяются условия:

- `workers >= 1`;
- `batchSize >= 1`;
- `pollInterval > 0`;
- `claimTransactionTimeout > 0`;
- `lockTimeout > kafkaSendTimeout`;
- `maxAttempts >= 1`;
- `retry.initialInterval > 0`;
- `retry.multiplier >= 1`;
- `retry.maxInterval >= retry.initialInterval`;
- `retry.jitter` находится в диапазоне от `0.0` до `1.0`;
- `shutdownTimeout > 0`.

Ошибка конфигурации запрещает запуск обработчика.

## 4. Идентификатор экземпляра

При старте обработчик создаёт `publisherInstance`:

```text
<hostname>:<processId>:<instanceUuid>
```

Пример:

```text
fi-ap-01:1842:419f63be-0745-43e7-b7fa-88cdeaf178db
```

Значение записывается в каждую попытку и позволяет определить, какой процесс
захватил событие.

## 5. Состояние события

Состояние публикации определяется по попытке с максимальным `attempt_number`:

- попыток нет — событие готово к первой отправке;
- `PROCESSING` и `locked_until > now()` — событие обрабатывается;
- `PROCESSING` и `locked_until <= now()` — попытка зависла;
- `FAILED` с заполненным `next_attempt_at` — ожидается повтор;
- `FAILED` без `next_attempt_at` — дальнейшие автоматические повторы запрещены;
- `INTERRUPTED` — предыдущий обработчик не завершил отправку;
- `PUBLISHED` — событие успешно опубликовано и больше не выбирается.

## 6. Условия выборки

Событие может быть выбрано, если выполняется одно из условий:

1. для него ещё нет попыток;
2. последняя попытка имеет статус `FAILED`, её `next_attempt_at <= now()`, а
   `attempt_number < maxAttempts`;
3. последняя попытка имеет статус `INTERRUPTED`, а
   `attempt_number < maxAttempts`;
4. последняя попытка имеет статус `PROCESSING`, но `locked_until <= now()`.

Не выбираются события:

- с последней попыткой `PUBLISHED`;
- с действующей попыткой `PROCESSING`;
- с исчерпанным `maxAttempts`, кроме зависшей попытки `PROCESSING`, которую необходимо
  завершить статусом `INTERRUPTED`;
- ожидающие наступления `next_attempt_at`;
- имеющие более раннее неопубликованное событие с тем же `message_key`.

Последнее правило не допускает отправку изменения позиции раньше предшествующего
события этой позиции.

События сортируются:

```sql
ORDER BY outbox.created_at, outbox.event_id
```

Сначала обрабатываются наиболее старые события. `event_id` обеспечивает стабильный
порядок при одинаковом `created_at`.

## 7. Атомарный захват

Каждый цикл обработчика открывает короткую транзакцию PostgreSQL. Максимальное
количество выбираемых событий определяется так:

```text
claimLimit = min(batchSize, количество свободных workers)
```

Строки `outbox` блокируются:

```sql
FOR UPDATE OF outbox SKIP LOCKED
LIMIT :claimLimit
```

`SKIP LOCKED` позволяет нескольким экземплярам обработчика параллельно выбирать
разные события без ожидания блокировок.

Для каждого выбранного события в той же транзакции:

1. зависшая последняя попытка `PROCESSING`, если она есть, переводится в
   `INTERRUPTED`;
2. вычисляется `attempt_number = previous_attempt_number + 1`, либо `1` для первой
   попытки;
3. если лимит попыток не исчерпан, создаётся новая запись
   `outbox_delivery_attempts`:

   ```text
   status             = PROCESSING
   started_at         = now()
   finished_at        = NULL
   next_attempt_at    = NULL
   publisher_instance = текущий publisherInstance
   locked_until       = now() + lockTimeout
   ```

4. транзакция фиксируется;
5. событие с созданной попыткой передаётся свободному worker.

Блокировка строки `outbox` и уникальное ограничение
`(event_id, attempt_number)` не позволяют создать две одновременные попытки одного
события.

Kafka-вызов не выполняется внутри транзакции PostgreSQL.

## 8. Публикация в Kafka

Worker формирует Kafka record:

```text
topic = outbox.topic
key   = outbox.message_key
value = outbox.payload
```

В Kafka headers передаются:

```text
eventId
eventType
eventVersion
producerSystem
```

Отправка выполняется через `franz-go`. Worker ожидает подтверждение Kafka не дольше
`kafkaSendTimeout`.

В каждый момент времени допускается только одна активная отправка для одного
`message_key`. Вместе с правилом выборки это сохраняет порядок событий конкретной
открытой позиции.

## 9. Успешная попытка

После подтверждения Kafka обработчик обновляет только созданную запись попытки:

```text
status         = PUBLISHED
finished_at    = now()
partition      = подтверждённая Kafka partition
offset_value   = подтверждённый Kafka offset
error_message  = NULL
next_attempt_at = NULL
```

Обновление выполняется по `outbox_delivery_attempts.id` с дополнительным условием:

```sql
WHERE id = :attemptId
  AND status = 'PROCESSING'
  AND publisher_instance = :publisherInstance
```

Если обновлена не одна строка, результат считается конфликтом владения и
фиксируется как ошибка обработчика.

## 10. Неуспешная попытка

При ошибке или истечении `kafkaSendTimeout` попытка переводится в `FAILED`:

```text
status        = FAILED
finished_at   = now()
error_message = безопасное диагностическое сообщение
```

Если ошибка допускает повтор и `attempt_number < maxAttempts`, рассчитывается
`next_attempt_at`. В остальных случаях `next_attempt_at` остаётся `NULL`, и ошибка
считается окончательной.

Без повторов завершаются:

- некорректный локальный `payload`;
- недопустимые `topic` или `message_key`;
- ошибка сериализации;
- иная ошибка, признанная конфигурационной или постоянной.

Ошибки соединения, таймауты и временные ошибки Kafka повторяются до достижения
`maxAttempts`.

## 11. Интервалы повторов

Базовая задержка для попытки с номером `N`:

```text
baseDelay =
  min(
    retry.initialInterval * retry.multiplier^(N - 1),
    retry.maxInterval
  )
```

Итоговая задержка с jitter:

```text
delay = baseDelay * random(1 - retry.jitter, 1 + retry.jitter)
next_attempt_at = finished_at + delay
```

При настройках по умолчанию базовые интервалы после неуспешных попыток составляют:

```text
после попытки 1: 1s
после попытки 2: 2s
после попытки 3: 4s
после попытки 4: 8s
```

После пятой попытки лимит исчерпан и следующий интервал не рассчитывается. Jitter
рассчитывается отдельно для каждого события.

## 12. Восстановление зависшей попытки

Попытка считается зависшей, если:

```text
status = PROCESSING
AND locked_until <= now()
```

При следующем захвате события обработчик в одной транзакции:

1. изменяет статус зависшей попытки на `INTERRUPTED`;
2. заполняет `finished_at = now()`;
3. записывает причину в `error_message`;
4. создаёт следующую попытку `PROCESSING`, если лимит не исчерпан.

Истечение блокировки не доказывает, что Kafka не получила сообщение. Новая попытка
может создать дубль, поэтому `event_id` не изменяется.

## 13. Штатное завершение

После получения сигнала завершения обработчик:

1. прекращает новые циклы выборки;
2. не захватывает дополнительные события;
3. ожидает активные workers не дольше `shutdownTimeout`;
4. фиксирует результаты завершившихся отправок;
5. отменяет оставшиеся Kafka-запросы;
6. завершает процесс.

Незавершённые попытки остаются `PROCESSING`. Другой запуск сможет восстановить их
после `locked_until`.

## 14. Наблюдаемость

Для каждого захвата и результата попытки журналируются:

- `eventId`;
- `attemptId`;
- `attemptNumber`;
- `publisherInstance`;
- `messageKey`;
- `status`;
- длительность отправки;
- Kafka partition и offset;
- категория ошибки.

Минимальные метрики:

```text
outbox_pending_events
outbox_processing_events
outbox_published_total
outbox_failed_attempts_total
outbox_interrupted_attempts_total
outbox_publish_duration_seconds
outbox_oldest_pending_age_seconds
```

## 15. Критерии приёмки

1. Одно событие не имеет двух одновременно действующих попыток.
2. Несколько экземпляров обработчика не захватывают одну запись одновременно.
3. Успешное событие не выбирается повторно.
4. Временная ошибка приводит к повтору согласно рассчитанному интервалу.
5. После `maxAttempts` автоматические повторы прекращаются.
6. Зависшая попытка становится `INTERRUPTED`.
7. События с одинаковым `message_key` публикуются последовательно.
8. Kafka-вызов не удерживает транзакцию PostgreSQL.
9. При сбое после публикации возможный дубль сохраняет прежний `event_id`.
10. История всех попыток остаётся доступной в `outbox_delivery_attempts`.

## 16. Время публикации

`publishedAt` исключён из payload `payment.demand`, поскольку фактическое время
публикации неизвестно в момент создания неизменяемой записи `outbox`.

Временные отметки имеют следующие назначения:

- `outbox.occurred_at` — время возникновения бизнес-события;
- `outbox.created_at` — время создания события в Outbox;
- `outbox_delivery_attempts.started_at` — время начала попытки;
- `outbox_delivery_attempts.finished_at` со статусом `PUBLISHED` — время получения
  подтверждения Kafka.

Факт публикации дополнительно подтверждается заполненными `partition` и
`offset_value`. Эти данные используются для технического мониторинга и не добавляются
в payload события.

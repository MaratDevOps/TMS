# Ручной тест: Повторный прогон

## 1. Назначение

Проверить, что **второй запуск** того же сценария на **том же окружении** (без очистки БД и Kafka) добавляет новые данные и **не портит результаты первого прогона**.

| Элемент | Значение |
|---|---|
| Идентификатор | MT-FI-AP-ITEST-02 |
| Базовый тест | [MT-FI-AP-ITEST-01](Ручной_тест_TestGenerateAndPublishPaymentDemand.md) |
| Конфигурация | `configs/itest-manual.yaml`, сценарий `itest` |
| За один запуск | **3** позиции / **3** события |

**Критерий успеха:** после второго прогона в системе **6** позиций и **6** опубликованных событий; данные первого прогона не изменились.

---

## 2. Предусловия

- Пройден [MT-FI-AP-ITEST-01](Ручной_тест_TestGenerateAndPublishPaymentDemand.md) (`exitCode: 0`, 3 позиции).
- Контейнеры PostgreSQL и Kafka **не пересоздавали** — те же, что после первого прогона.
- Перед вторым запуском зафиксируйте **контрольные значения** (сохраните в заметку):

```sql
SELECT COUNT(*) FROM open_vendor_items;          -- ожидается 3
SELECT COUNT(*) FROM outbox;                       -- ожидается 3
SELECT COUNT(*) FROM outbox_delivery_attempts
WHERE status = 'PUBLISHED';                        -- ожидается 3
```

Сохраните UUID и ключи первого прогона:

```sql
SELECT id, source_line_item_id, document_number, created_at
FROM open_vendor_items
ORDER BY created_at;
```

---

## 3. Действие

Из `services/fi-ap` выполните **тот же запуск**, что в MT-FI-AP-ITEST-01:

```powershell
go run ./cmd/fi-ap-generator --config configs/itest-manual.yaml --scenario itest 1> result-run2.yaml 2> run2.log
echo $LASTEXITCODE
```

> БД и Kafka **не очищать**.

---

## 4. Ожидаемые результаты

### 4.1. Итог второго запуска (YAML)

| Поле | Ожидание |
|---|---|
| `exitCode` | `0` |
| `status` | `COMPLETED` |
| `createdPositions` | `3` |
| `publishedEvents` | `3` |
| `generationErrors` | `0` |
| `publicationErrors` | `0` |
| `runId` | **новый** UUID, отличный от первого прогона |

### 4.2. Накопление данных в PostgreSQL

| Объект | После 1-го прогона | После 2-го прогона |
|---|---:|---:|
| `open_vendor_items` | 3 | **6** |
| `origin_documents` | 3 | **6** |
| `outbox` | 3 | **6** |
| `outbox_delivery_attempts` (`PUBLISHED`) | 3 | **6** |

Проверка:

```sql
SELECT COUNT(*) FROM open_vendor_items;
SELECT COUNT(*) FROM origin_documents;
SELECT COUNT(*) FROM outbox;
SELECT COUNT(*) FROM outbox_delivery_attempts WHERE status = 'PUBLISHED';
```

### 4.3. Данные первого прогона не изменились

| Проверка | Ожидание |
|---|---|
| Количество строк с `id` из первого прогона | без изменений (3 строки на месте) |
| `source_line_item_id` первого прогона | те же значения, что зафиксированы до 2-го запуска |
| `document_number` первого прогона | те же значения |
| Статус публикации старых событий | по-прежнему `PUBLISHED`, без новых попыток |

```sql
-- подставьте id из первого прогона
SELECT id, source_line_item_id, document_number
FROM open_vendor_items
WHERE id IN ('<uuid-1>', '<uuid-2>', '<uuid-3>');

SELECT event_id, COUNT(*) AS attempt_count
FROM outbox_delivery_attempts
WHERE event_id IN (
    SELECT event_id FROM outbox
    WHERE aggregate_id IN ('<uuid-1>', '<uuid-2>', '<uuid-3>')
)
GROUP BY event_id;
```

**Ожидание:** у каждого старого `event_id` — **одна** успешная попытка (`attempt_count = 1`).

### 4.4. Новые записи не дублируют старые

| Поле | Ожидание |
|---|---|
| `open_vendor_items.id` | 3 **новых** UUID, не пересекаются с первым прогоном |
| `source_line_item_id` | 3 **новых** значения, все 6 уникальны |
| `document_number` | новые номера **больше** номеров первого прогона (sequence `fi_document_number_seq`) |
| `outbox.event_id` | 3 новых UUID |

```sql
SELECT source_line_item_id, COUNT(*)
FROM open_vendor_items
GROUP BY source_line_item_id
HAVING COUNT(*) > 1;
-- ожидается 0 строк

SELECT document_number FROM open_vendor_items ORDER BY document_number;
-- ожидается 6 различных номеров, монотонный рост
```

### 4.5. Kafka

| Проверка | Ожидание |
|---|---|
| Сообщений текущего (2-го) прогона | **3** |
| Kafka key 2-го прогона | не пересекаются с key 1-го прогона |
| Старые сообщения | остаются в топике, payload не меняется |

Ключи 2-го прогона (последние 3 записи Outbox):

```sql
SELECT message_key, created_at
FROM outbox
ORDER BY created_at DESC
LIMIT 3;
```

## 5. Чек-лист

- [ ] Второй запуск: `exitCode = 0`, `createdPositions = 3`, `publishedEvents = 3`
- [ ] В БД стало **6** позиций, **6** outbox, **6** `PUBLISHED`
- [ ] 3 записи первого прогона на месте, поля не изменились
- [ ] У старых событий нет повторных попыток публикации
- [ ] Все 6 `source_line_item_id` уникальны
- [ ] Новые `document_number` отличаются от первого прогона
- [ ] В Kafka появились 3 новых сообщения с новыми key

**Тест пройден**, если все пункты выполнены.

---

## 6. Типовые отклонения

| Наблюдение | Вероятная проблема |
|---|---|
| `createdPositions < 3` | Конфликт уникальности / ошибка генерации |
| Счётчик не вырос до 6 | Данные перезаписались или прогон не завершился |
| Дубли `source_line_item_id` | Нарушена изоляция между запусками |
| У старых `event_id` больше одной `PUBLISHED`-попытки | Повторная публикация уже отправленных событий |
| `exitCode: 0`, но счётчики не выросли | Проверяете не ту БД / не тот стенд |

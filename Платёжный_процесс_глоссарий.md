# Описание элементов платёжного процесса

Справочник по элементам схемы сквозного платёжного процесса SAP Treasury
(`Платёжный_процесс_базовый.PlantUml` / `Платёжный_процесс_полный.PlantUml`).

Каждый элемент описывается по единой структуре: суть, источник/вход, результат/выход,
роль, ключевые атрибуты, статус.

---

## ERP (FI/MM/SD)

### Incoming Payment Request Demand / Входящая потребность в заявке на оплату

Первый шаг процесса и точка его запуска (триггер). Это ещё не платёж и не формальная
заявка, а бизнес-событие, из которого возникает потребность в оплате.

- **Суть.** Момент, когда в операционных модулях ERP появляется обязательство или
  необходимость произвести платёж. Запускает весь сквозной процесс.
- **Источники (типовые в SAP).**
  - MM (закупки): проведённый счёт поставщика (`MIRO`), открытая позиция кредитора (`FI-AP`).
  - SD/FI: возвраты покупателям, кредит-ноты, авансы.
  - FI напрямую: налоги, зарплата, платежи по договорам, ручные заявки.
  - TRM: расчёты по финансовым инструментам, займам, депозитам.
- **Результат/выход.** Потребность передаётся на следующий шаг
  `Generate Payment Request / Формирование заявки на оплату`, где формализуется в объект-заявку.
- **Роль (RACI).** Заявитель / бизнес-подразделение — R (исполнитель), A (ответственный).
- **Ключевые атрибуты.** Сумма, валюта, контрагент, срок оплаты (due date),
  основание / ссылка на документ-источник, источник потребности (MM/SD/FI/TRM).
- **Статус.** Пред-статус: формального статуса у объекта платежа ещё нет; статус
  `Created / Создан` присваивается на следующем шаге.

### Generate Payment Request / Формирование заявки на оплату

Второй шаг в партиции ERP: неформальная потребность превращается в структурированный
документ-заявку на оплату, пригодный для передачи в казначейскую систему.

- **Суть.** Формализация входящей потребности в объект «заявка на оплату» с полным
  набором платёжных реквизитов. Именно с этого момента появляется управляемый объект.
- **Источник/вход.** Результат предыдущего шага
  `Incoming Payment Request Demand / Входящая потребность в заявке на оплату`
  вместе с данными документа-источника (счёт, договор, сделка) и мастер-данными контрагента.
- **Что формируется (типовое в SAP).**
  - Платёжная заявка (Payment Request, тип F111 / TRM) или предпосылка для платёжной программы `F110`.
  - Реквизиты: сумма, валюта, получатель, банковские реквизиты (IBAN/BIC), срок оплаты,
    способ оплаты (payment method), назначение платежа, основание.
- **Результат/выход.** Готовая заявка передаётся в казначейскую систему на шаг
  `Import Payment Request / Импорт запроса на оплату`.
- **Роль (RACI).** Заявитель / бизнес-подразделение — R (исполнитель);
  бизнес-подразделение — A (ответственный).
- **Ключевые атрибуты.** Сумма, валюта, контрагент, IBAN/BIC, срок оплаты (due date),
  способ оплаты, приоритет/срочность, ссылка на документ-источник.
- **Статус.** По завершении шага объект получает статус `Created / Создан`.
- **Типичные ошибки/риски.** Неполные или неверные банковские реквизиты, некорректный
  срок оплаты, отсутствие способа оплаты — приводят к ошибке на шаге `Validate Request`.

## Treasury & Risk Management (Казначейство и управление рисками)

### Import Payment Request / Импорт запроса на оплату

Первый шаг казначейской системы: заявка на оплату, сформированная в ERP, принимается
в модуль TRM для дальнейшей обработки. Открывает цикл «импорт → проверка» (`repeat`).

- **Суть.** Приём заявки из ERP в казначейскую систему и её регистрация как входящего
  объекта для обработки. Граница ответственности переходит от ERP к казначейству.
- **Источник/вход.** Заявка, сформированная на шаге
  `Generate Payment Request / Формирование заявки на оплату` (статус `Created / Создан`).
- **Как выполняется (типовое в SAP).**
  - Передача через интерфейс/промежуточный слой (IDoc, PI/PO, BAPI, ALE) или пакетную загрузку.
  - Может быть единичная заявка или пакет (batch) заявок.
  - Первичная техническая приёмка: проверка формата, полноты полей, отсутствия дублей на уровне интеграции.
- **Результат/выход.** Импортированная заявка передаётся на шаг
  `Validate Request / Проверка запроса`. При неуспехе валидации цикл возвращает управление
  сюда через `Send Validation Error & Correct Request (ERP)`.
- **Роль (RACI).** Казначей / система TRM — R (исполнитель);
  руководитель казначейства — A (ответственный).
- **Ключевые атрибуты.** Идентификатор заявки, ссылка на документ-источник ERP,
  канал/интерфейс импорта, признак пакета, метка времени приёма.
- **Статус.** Объект остаётся в статусе `Created / Создан` до успешной проверки
  (`Validated / Проверен`).
- **Типичные ошибки/риски.** Сбой интерфейса, потеря/задержка сообщения, дубли при
  повторной передаче, несоответствие формата — обрабатываются на уровне интеграции и валидации.

### Validate Request / Проверка запроса

Второй шаг цикла в TRM: содержательная проверка импортированной заявки на корректность
и полноту перед созданием управляемого объекта платежа. Завершается развилкой
`Validation successful? / Проверка успешна?`.

- **Суть.** Контроль качества заявки — соответствие данных, реквизитов и бизнес-правил.
  Отсекает некорректные заявки до их дальнейшей обработки.
- **Источник/вход.** Импортированная заявка с шага
  `Import Payment Request / Импорт запроса на оплату` (статус `Created / Создан`).
- **Что проверяется (типовое в SAP).**
  - Полнота обязательных полей (сумма, валюта, получатель, срок, способ оплаты).
  - Корректность банковских реквизитов: формат и контрольный разряд IBAN, соответствие BIC.
  - Мастер-данные контрагента (существование, блокировки, банковские счета).
  - Бизнес-правила: лимиты, допустимые валюты/способы оплаты, счёт house bank.
  - Технические проверки: ссылочная целостность с документом-источником и
    **технический контроль дублей заявки** — не была ли одна и та же заявка (по
    идентификатору заявки и ссылке на документ-источник ERP) импортирована дважды
    (идемпотентность приёма).
- **Отличие от `Duplicate Payment Check`.** Здесь ловятся *технические* дубли заявки
  на входе (повторный импорт того же документа/IDoc). Бизнес-контроль дублей платежей
  по существу (получатель + сумма + инвойс + период) выполняется отдельно на шаге
  `Duplicate Payment Check / Контроль дублей платежей` в партиции комплаенса,
  непосредственно перед оплатой.
- **Результат/выход.**
  - Успех (`Yes / Да`) → шаг `Create Payment Request Object / Создание объекта запроса на оплату`.
  - Неуспех (`No / Нет`) → `Send Validation Error & Correct Request (ERP)` и возврат в начало
    цикла на повторный `Import Payment Request`.
- **Роль (RACI).** Казначей / система TRM — R (исполнитель);
  руководитель казначейства — A (ответственный).
- **Ключевые атрибуты.** Результат проверки (успех/ошибка), перечень выявленных ошибок,
  проверенные реквизиты, метка времени валидации.
- **Статус.** При успехе объект переходит в `Validated / Проверен`; при ошибке остаётся
  `Created / Создан` до исправления в ERP и повторного импорта.
- **Типичные ошибки/риски.** Неверный IBAN/BIC, заблокированный или несуществующий
  контрагент, нарушение лимитов, неполные реквизиты, обнаруженный технический дубль заявки.

### Create Payment Request Object / Создание объекта запроса на оплату

Шаг после успешной валидации: на основе проверенной заявки создаётся управляемый
объект платежа в казначейской системе — «золотая запись», с которой работает весь
дальнейший процесс.

- **Суть.** Материализация проверенной заявки в постоянный объект TRM с уникальным
  идентификатором и жизненным циклом (статусами). До этого шага заявка — входные данные,
  после — управляемая сущность системы.
- **Источник/вход.** Успешно проверенная заявка с шага
  `Validate Request / Проверка запроса` (статус `Validated / Проверен`).
- **Что создаётся (типовое в SAP).**
  - Объект Payment Request в TRM (например, категория платежа/операции) с присвоением
    внутреннего номера.
  - Привязка к документу-источнику ERP, контрагенту, house bank/банковскому счёту.
  - Заполнение платёжных атрибутов, признаков способа оплаты и даты валютирования.
- **Результат/выход.** Созданный объект направляется в цикл согласования
  `Approval Workflow / Процесс согласования`.
- **Роль (RACI).** Казначей / система TRM — R (исполнитель);
  руководитель казначейства — A (ответственный).
- **Ключевые атрибуты.** Внутренний идентификатор объекта, ссылка на заявку и
  документ-источник, контрагент, сумма, валюта, срок оплаты, способ оплаты, house bank.
- **Статус.** Объект фиксируется в системе; в статусной модели соответствует
  подтверждённому `Validated / Проверен` и готов к переходу в `Approved / Согласован`.
- **Типичные ошибки/риски.** Некорректная привязка к контрагенту/счёту, дублирующее
  создание объекта при повторной обработке, неполное наследование атрибутов из заявки.

### Approval Workflow / Процесс согласования

Цикл авторизации объекта платежа: ответственные лица подтверждают или отклоняют платёж.
Реализован как петля `repeat … repeat while (Resubmitted after rework?)` с фиксацией
причины отказа и возможностью доработки.

- **Суть.** Управляемая авторизация: платёж не может двигаться дальше без согласования.
  Обеспечивает контроль полномочий и разделение обязанностей (SoD, «четыре глаза»).
- **Источник/вход.** Созданный объект платежа с шага
  `Create Payment Request Object / Создание объекта запроса на оплату`.
- **Как выполняется (типовое в SAP).**
  - Маршрут согласования (workflow) с одним или несколькими уровнями утверждения.
  - Обычно тиерность по сумме/типу платежа (лимиты подписи), правила замещения.
  - Действия согласующего: утвердить, отклонить, вернуть на доработку.
- **Ветви развилки `Approved? / Согласовано?`.**
  - `Yes / Да` → `Set Status: Approved / Статус: Согласовано`, выход из цикла.
  - `No / Нет` → `Record Rejection Reason / Фиксация причины отклонения`, затем развилка
    `Rework possible? / Возможна доработка?`:
    - `Yes / Да` → `Return to Initiator & Correct Request / Возврат инициатору и
      корректировка запроса` и повторная отправка на согласование (петля цикла);
    - `No / Нет` → `Cancel Request (Status: Rejected) / Отмена запроса (Статус: Отклонено)`,
      завершение процесса.
- **Результат/выход.** Согласованный объект передаётся в партицию
  `Compliance & Screening` (полная схема) или в `Cash Management` (базовая схема).
- **Роль (RACI).** Согласующий (Approver) — A (ответственный за решение);
  инициатор — C (консультируется при доработке); казначей — I (информируется).
- **Ключевые атрибуты.** Уровни и маршрут согласования, лимиты/пороги, решение,
  причина отклонения, согласующий, метки времени, признак повторной отправки.
- **Статус.** При утверждении — `Approved / Согласован`; при отказе без доработки —
  терминальный `Rejected / Отклонён`.
- **Типичные ошибки/риски.** Нарушение SoD (инициатор = согласующий), обход лимитов,
  «застревание» заявок без реакции согласующего, зацикливание доработки без результата,
  отсутствие зафиксированной причины отклонения.

## Compliance & Screening (Комплаенс и проверки)

### Sanctions List Screening / Проверка по санкционным спискам

Первый шаг партиции комплаенса: проверка участников платежа по санкционным и «стоп»-спискам
до его исполнения. Обязательный регуляторный контроль в казначействе.

- **Суть.** Скрининг контрагента и связанных сторон платежа против санкционных перечней,
  чтобы не допустить платёж в адрес запрещённого лица/юрисдикции.
- **Источник/вход.** Согласованный объект платежа (статус `Approved / Согласован`) с шага
  `Approval Workflow / Процесс согласования`.
- **Что проверяется (типовое в SAP).**
  - Стороны: получатель, банк получателя, банки-посредники, при необходимости — конечный бенефициар.
  - Списки: OFAC (SDN), EU, UN, HMT/OFSI, локальные перечни ЦБ/регуляторов.
  - Реквизиты: наименование, адрес, страна, BIC/банк, ключевые слова назначения платежа.
  - Технология: нечёткое сопоставление (fuzzy matching), контроль запрещённых юрисдикций.
  - Интеграция: SAP Watch List Screening (GTS) или внешний провайдер скрининга.
- **Результат/выход.** При отсутствии совпадений — переход к `AML Check / Проверка AML`.
  При совпадении (hit) — эскалация в общий контроль комплаенса
  (`Compliance passed? / Комплаенс пройден?` → `Hold & Investigate`).
- **Роль (RACI).** Комплаенс-офицер — R/A (исполняет и отвечает);
  казначей — I (информируется), санкционный/юридический эксперт — C.
- **Ключевые атрибуты.** Использованные списки и их версия/дата, результат (чисто/совпадение),
  оценка совпадения (score), проверенные стороны, метка времени, решение по hit.
- **Статус.** Промежуточный контроль в рамках перехода к `Compliant / Комплаенс пройден`;
  при подтверждённом совпадении ведёт к терминальному `Compliance Rejected / Отклонён комплаенсом`.
- **Типичные ошибки/риски.** Ложные срабатывания (false positive) и их избыточная доля,
  пропуск совпадения (false negative), устаревшие версии списков, неполный набор
  проверяемых сторон, отсутствие аудита решений по совпадениям.

### AML Check / Проверка AML (ПОД/ФТ)

Второй шаг комплаенса: контроль на противодействие отмыванию доходов и финансированию
терроризма (ПОД/ФТ). В отличие от санкционного скрининга «по спискам», здесь оценивается
характер и риск самой операции.

- **Суть.** Оценка платежа на признаки подозрительной активности и соответствие
  риск-профилю контрагента, чтобы предотвратить использование платежа в схемах
  отмывания/финансирования терроризма.
- **Источник/вход.** Объект платежа, прошедший `Sanctions List Screening / Проверка по
  санкционным спискам` (совпадений нет).
- **Что проверяется (типовое).**
  - Профиль риска контрагента (KYC/CDD), статус PEP (публичные должностные лица).
  - Поведенческие правила и сценарии: необычные суммы, частота, дробление (structuring),
    отклонение от типового профиля.
  - Юрисдикции повышенного риска, транзит через рисковые страны/банки.
  - Назначение платежа и экономический смысл операции.
  - Интеграция: специализированная AML-система/провайдер, риск-скоринг.
- **Результат/выход.** При приемлемом риске — переход к `Duplicate Payment Check / Контроль
  дублей платежей`. При срабатывании правил — эскалация в общий контроль
  (`Compliance passed?` → `Hold & Investigate`), при необходимости — формирование SAR/STR
  (сообщение о подозрительной операции).
- **Роль (RACI).** Комплаенс-офицер / AML-аналитик — R/A;
  казначей — I; юридический/риск-эксперт — C.
- **Ключевые атрибуты.** Риск-скор операции, сработавшие сценарии/правила, статус KYC/PEP,
  решение (пропустить/эскалировать), признак формирования SAR/STR, метка времени.
- **Статус.** Промежуточный контроль на пути к `Compliant / Комплаенс пройден`;
  при подтверждённом риске ведёт к терминальному `Compliance Rejected / Отклонён комплаенсом`.
- **Типичные ошибки/риски.** Устаревшие данные KYC, неоткалиброванные сценарии (много
  ложных срабатываний или пропуски), необнаруженный structuring, отсутствие аудита
  и своевременного SAR/STR, «ручные» исключения без обоснования.

### Duplicate Payment Check / Контроль дублей платежей

Третий шаг комплаенса: проверка на повторную оплату по существу — не платим ли мы дважды
за одно и то же обязательство. Это бизнес-контроль дублей, в отличие от технического
контроля на шаге `Validate Request`.

- **Суть.** Предотвращение повторного платежа даже тогда, когда заявки формально разные,
  созданы из разных источников или в разное время. Финальный барьер перед оплатой.
- **Источник/вход.** Объект платежа, прошедший `AML Check / Проверка AML (ПОД/ФТ)`.
- **Что проверяется (типовое в SAP).**
  - Совпадение бизнес-признаков: получатель + сумма + валюта + номер счёта/инвойса.
  - Скользящее окно (например, платежи за N дней) и «похожие» платежи (fuzzy).
  - Уже исполненные и находящиеся в обработке платежи (в т.ч. в предложениях/поручениях).
  - Стандартный контроль дублей кредиторских счетов SAP (проверка по ссылке/reference).
- **Отличие от контроля дублей в `Validate Request`.** Там — *технический* дубль заявки
  (повторный импорт одного документа/IDoc, идемпотентность приёма). Здесь — *бизнес*-дубль
  платежа по существу (одно и то же обязательство оплачивается повторно).
- **Результат/выход.** При отсутствии дублей — переход к развилке
  `Compliance passed? / Комплаенс пройден?` и далее `Set Status: Compliant`.
  При обнаружении дубля — `Hold & Investigate (Compliance)` и разбор.
- **Роль (RACI).** Комплаенс-офицер / казначей — R; руководитель казначейства — A;
  бухгалтерия (AP) — C.
- **Ключевые атрибуты.** Набор признаков сравнения, размер окна, найденные кандидаты-дубли,
  оценка схожести, решение (пропустить/удержать), метка времени.
- **Статус.** Промежуточный контроль на пути к `Compliant / Комплаенс пройден`;
  подтверждённый дубль ведёт к удержанию и возможной отмене платежа.
- **Типичные ошибки/риски.** Пропуск дубля из-за расхождений в реквизитах (разный формат
  инвойса), слишком узкое окно сравнения, избыточные ложные срабатывания, ручное снятие
  блокировки без проверки, дубли между разными системами-источниками.

### Compliance passed? / Комплаенс пройден? (развилка и обработка результата)

Итоговая развилка партиции комплаенса: по совокупным результатам санкционного скрининга,
AML и контроля дублей принимается решение — пропустить платёж дальше или удержать.
Включает шаги `Set Status: Compliant`, `Hold & Investigate` и вложенную развилку
`Cleared after investigation?`.

- **Суть.** Единая точка принятия комплаенс-решения по платежу: агрегирует результаты
  предыдущих проверок и определяет дальнейший маршрут.
- **Источник/вход.** Результаты шагов `Sanctions List Screening`, `AML Check` и
  `Duplicate Payment Check` по одному объекту платежа.
- **Ветви развилки.**
  - `Yes / Да` (все проверки чисто) → `Set Status: Compliant / Статус: Комплаенс пройден`,
    объект переходит в партицию `FX & Hedging`.
  - `No / Нет` (есть срабатывание) → `Hold & Investigate (Compliance) / Блокировка и
    расследование (комплаенс)`, затем вложенная развилка
    `Cleared after investigation? / Снято после расследования?`:
    - `Yes / Да` → платёж реабилитирован, продолжает движение по процессу;
    - `No / Нет` → `Cancel Payment (Status: Compliance Rejected) / Отмена платежа
      (Статус: Отклонён комплаенсом)`, завершение процесса.
- **Связанные шаги.**
  - `Set Status: Compliant` — фиксация успешного прохождения комплаенса как статуса объекта.
  - `Hold & Investigate` — временное удержание с ручным разбором совпадения/срабатывания
    (документирование решения, привлечение экспертов).
  - `Cleared after investigation?` — результат расследования: ложное срабатывание снимается,
    подтверждённое нарушение ведёт к отмене.
- **Результат/выход.** Либо `Compliant / Комплаенс пройден` и переход к FX/хеджированию,
  либо терминальный `Compliance Rejected / Отклонён комплаенсом`.
- **Роль (RACI).** Комплаенс-офицер — A (принимает решение); AML/санкционный аналитик — R;
  казначей — I; юридический эксперт — C.
- **Ключевые атрибуты.** Сводный результат проверок, основание удержания, ход и итог
  расследования, обоснование снятия/отклонения, ответственный, метки времени (для аудита).
- **Статус.** `Compliant / Комплаенс пройден` при успехе; `Compliance Rejected /
  Отклонён комплаенсом` при подтверждённом нарушении.
- **Типичные ошибки/риски.** Снятие удержания без должного обоснования, затягивание
  расследования (просрочка платежа), отсутствие аудиторского следа по решению,
  конфликт интересов (решение принимает заинтересованное лицо).

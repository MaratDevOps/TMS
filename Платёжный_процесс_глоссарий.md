# Описание элементов платёжного процесса

Справочник по элементам схемы сквозного платёжного процесса SAP Treasury
(`Платёжный_процесс_базовый.PlantUml` / `Платёжный_процесс_полный.PlantUml`).

Каждый элемент описывается по единой структуре: суть, источник/вход, результат/выход,
роль, ключевые атрибуты, статус.

---

## ERP (FI/MM/SD)

### Incoming Payment Request Demand / Входящая потребность в заявке на оплату

Первый шаг процесса и точка его запуска (триггер). Это ещё не платёж и не формальная
заявка, а бизнес-событие, из которого возникает потребность в оплате.

- **Суть.** Момент, когда в операционных модулях ERP появляется обязательство или
  необходимость произвести платёж. Запускает весь сквозной процесс.
- **Источники (типовые в SAP).**
  - MM (закупки): проведённый счёт поставщика (`MIRO`), открытая позиция кредитора (`FI-AP`).
  - SD/FI: возвраты покупателям, кредит-ноты, авансы.
  - FI напрямую: налоги, зарплата, платежи по договорам, ручные заявки.
  - TRM: расчёты по финансовым инструментам, займам, депозитам.
- **Результат/выход.** Потребность передаётся на следующий шаг
  `Generate Payment Request / Формирование заявки на оплату`, где формализуется в объект-заявку.
- **Роль (RACI).** Заявитель / бизнес-подразделение — R (исполнитель), A (ответственный).
- **Ключевые атрибуты.** Сумма, валюта, контрагент, срок оплаты (due date),
  основание / ссылка на документ-источник, источник потребности (MM/SD/FI/TRM).
- **Статус.** Пред-статус: формального статуса у объекта платежа ещё нет; статус
  `Created / Создан` присваивается на следующем шаге.

### Generate Payment Request / Формирование заявки на оплату

Второй шаг в партиции ERP: неформальная потребность превращается в структурированный
документ-заявку на оплату, пригодный для передачи в казначейскую систему.

- **Суть.** Формализация входящей потребности в объект «заявка на оплату» с полным
  набором платёжных реквизитов. Именно с этого момента появляется управляемый объект.
- **Источник/вход.** Результат предыдущего шага
  `Incoming Payment Request Demand / Входящая потребность в заявке на оплату`
  вместе с данными документа-источника (счёт, договор, сделка) и мастер-данными контрагента.
- **Что формируется (типовое в SAP).**
  - Платёжная заявка (Payment Request, тип F111 / TRM) или предпосылка для платёжной программы `F110`.
  - Реквизиты: сумма, валюта, получатель, банковские реквизиты (IBAN/BIC), срок оплаты,
    способ оплаты (payment method), назначение платежа, основание.
- **Результат/выход.** Готовая заявка передаётся в казначейскую систему на шаг
  `Import Payment Request / Импорт запроса на оплату`.
- **Роль (RACI).** Заявитель / бизнес-подразделение — R (исполнитель);
  бизнес-подразделение — A (ответственный).
- **Ключевые атрибуты.** Сумма, валюта, контрагент, IBAN/BIC, срок оплаты (due date),
  способ оплаты, приоритет/срочность, ссылка на документ-источник.
- **Статус.** По завершении шага объект получает статус `Created / Создан`.
- **Типичные ошибки/риски.** Неполные или неверные банковские реквизиты, некорректный
  срок оплаты, отсутствие способа оплаты — приводят к ошибке на шаге `Validate Request`.

## Treasury & Risk Management (Казначейство и управление рисками)

### Import Payment Request / Импорт запроса на оплату

Первый шаг казначейской системы: заявка на оплату, сформированная в ERP, принимается
в модуль TRM для дальнейшей обработки. Открывает цикл «импорт → проверка» (`repeat`).

- **Суть.** Приём заявки из ERP в казначейскую систему и её регистрация как входящего
  объекта для обработки. Граница ответственности переходит от ERP к казначейству.
- **Источник/вход.** Заявка, сформированная на шаге
  `Generate Payment Request / Формирование заявки на оплату` (статус `Created / Создан`).
- **Как выполняется (типовое в SAP).**
  - Передача через интерфейс/промежуточный слой (IDoc, PI/PO, BAPI, ALE) или пакетную загрузку.
  - Может быть единичная заявка или пакет (batch) заявок.
  - Первичная техническая приёмка: проверка формата, полноты полей, отсутствия дублей на уровне интеграции.
- **Результат/выход.** Импортированная заявка передаётся на шаг
  `Validate Request / Проверка запроса`. При неуспехе валидации цикл возвращает управление
  сюда через `Send Validation Error & Correct Request (ERP)`.
- **Роль (RACI).** Казначей / система TRM — R (исполнитель);
  руководитель казначейства — A (ответственный).
- **Ключевые атрибуты.** Идентификатор заявки, ссылка на документ-источник ERP,
  канал/интерфейс импорта, признак пакета, метка времени приёма.
- **Статус.** Объект остаётся в статусе `Created / Создан` до успешной проверки
  (`Validated / Проверен`).
- **Типичные ошибки/риски.** Сбой интерфейса, потеря/задержка сообщения, дубли при
  повторной передаче, несоответствие формата — обрабатываются на уровне интеграции и валидации.

### Validate Request / Проверка запроса

Второй шаг цикла в TRM: содержательная проверка импортированной заявки на корректность
и полноту перед созданием управляемого объекта платежа. Завершается развилкой
`Validation successful? / Проверка успешна?`.

- **Суть.** Контроль качества заявки — соответствие данных, реквизитов и бизнес-правил.
  Отсекает некорректные заявки до их дальнейшей обработки.
- **Источник/вход.** Импортированная заявка с шага
  `Import Payment Request / Импорт запроса на оплату` (статус `Created / Создан`).
- **Что проверяется (типовое в SAP).**
  - Полнота обязательных полей (сумма, валюта, получатель, срок, способ оплаты).
  - Корректность банковских реквизитов: формат и контрольный разряд IBAN, соответствие BIC.
  - Мастер-данные контрагента (существование, блокировки, банковские счета).
  - Бизнес-правила: лимиты, допустимые валюты/способы оплаты, счёт house bank.
  - Технические проверки: ссылочная целостность с документом-источником и
    **технический контроль дублей заявки** — не была ли одна и та же заявка (по
    идентификатору заявки и ссылке на документ-источник ERP) импортирована дважды
    (идемпотентность приёма).
- **Отличие от `Duplicate Payment Check`.** Здесь ловятся *технические* дубли заявки
  на входе (повторный импорт того же документа/IDoc). Бизнес-контроль дублей платежей
  по существу (получатель + сумма + инвойс + период) выполняется отдельно на шаге
  `Duplicate Payment Check / Контроль дублей платежей` в партиции комплаенса,
  непосредственно перед оплатой.
- **Результат/выход.**
  - Успех (`Yes / Да`) → шаг `Create Payment Request Object / Создание объекта запроса на оплату`.
  - Неуспех (`No / Нет`) → `Send Validation Error & Correct Request (ERP)` и возврат в начало
    цикла на повторный `Import Payment Request`.
- **Роль (RACI).** Казначей / система TRM — R (исполнитель);
  руководитель казначейства — A (ответственный).
- **Ключевые атрибуты.** Результат проверки (успех/ошибка), перечень выявленных ошибок,
  проверенные реквизиты, метка времени валидации.
- **Статус.** При успехе объект переходит в `Validated / Проверен`; при ошибке остаётся
  `Created / Создан` до исправления в ERP и повторного импорта.
- **Типичные ошибки/риски.** Неверный IBAN/BIC, заблокированный или несуществующий
  контрагент, нарушение лимитов, неполные реквизиты, обнаруженный технический дубль заявки.

### Create Payment Request Object / Создание объекта запроса на оплату

Шаг после успешной валидации: на основе проверенной заявки создаётся управляемый
объект платежа в казначейской системе — «золотая запись», с которой работает весь
дальнейший процесс.

- **Суть.** Материализация проверенной заявки в постоянный объект TRM с уникальным
  идентификатором и жизненным циклом (статусами). До этого шага заявка — входные данные,
  после — управляемая сущность системы.
- **Источник/вход.** Успешно проверенная заявка с шага
  `Validate Request / Проверка запроса` (статус `Validated / Проверен`).
- **Что создаётся (типовое в SAP).**
  - Объект Payment Request в TRM (например, категория платежа/операции) с присвоением
    внутреннего номера.
  - Привязка к документу-источнику ERP, контрагенту, house bank/банковскому счёту.
  - Заполнение платёжных атрибутов, признаков способа оплаты и даты валютирования.
- **Результат/выход.** Созданный объект направляется в цикл согласования
  `Approval Workflow / Процесс согласования`.
- **Роль (RACI).** Казначей / система TRM — R (исполнитель);
  руководитель казначейства — A (ответственный).
- **Ключевые атрибуты.** Внутренний идентификатор объекта, ссылка на заявку и
  документ-источник, контрагент, сумма, валюта, срок оплаты, способ оплаты, house bank.
- **Статус.** Объект фиксируется в системе; в статусной модели соответствует
  подтверждённому `Validated / Проверен` и готов к переходу в `Approved / Согласован`.
- **Типичные ошибки/риски.** Некорректная привязка к контрагенту/счёту, дублирующее
  создание объекта при повторной обработке, неполное наследование атрибутов из заявки.

### Approval Workflow / Процесс согласования

Цикл авторизации объекта платежа: ответственные лица подтверждают или отклоняют платёж.
Реализован как петля `repeat … repeat while (Resubmitted after rework?)` с фиксацией
причины отказа и возможностью доработки.

- **Суть.** Управляемая авторизация: платёж не может двигаться дальше без согласования.
  Обеспечивает контроль полномочий и разделение обязанностей (SoD, «четыре глаза»).
- **Источник/вход.** Созданный объект платежа с шага
  `Create Payment Request Object / Создание объекта запроса на оплату`.
- **Как выполняется (типовое в SAP).**
  - Маршрут согласования (workflow) с одним или несколькими уровнями утверждения.
  - Обычно тиерность по сумме/типу платежа (лимиты подписи), правила замещения.
  - Действия согласующего: утвердить, отклонить, вернуть на доработку.
- **Ветви развилки `Approved? / Согласовано?`.**
  - `Yes / Да` → `Set Status: Approved / Статус: Согласовано`, выход из цикла.
  - `No / Нет` → `Record Rejection Reason / Фиксация причины отклонения`, затем развилка
    `Rework possible? / Возможна доработка?`:
    - `Yes / Да` → `Return to Initiator & Correct Request / Возврат инициатору и
      корректировка запроса` и повторная отправка на согласование (петля цикла);
    - `No / Нет` → `Cancel Request (Status: Rejected) / Отмена запроса (Статус: Отклонено)`,
      завершение процесса.
- **Результат/выход.** Согласованный объект передаётся в партицию
  `Compliance & Screening` (полная схема) или в `Cash Management` (базовая схема).
- **Роль (RACI).** Согласующий (Approver) — A (ответственный за решение);
  инициатор — C (консультируется при доработке); казначей — I (информируется).
- **Ключевые атрибуты.** Уровни и маршрут согласования, лимиты/пороги, решение,
  причина отклонения, согласующий, метки времени, признак повторной отправки.
- **Статус.** При утверждении — `Approved / Согласован`; при отказе без доработки —
  терминальный `Rejected / Отклонён`.
- **Типичные ошибки/риски.** Нарушение SoD (инициатор = согласующий), обход лимитов,
  «застревание» заявок без реакции согласующего, зацикливание доработки без результата,
  отсутствие зафиксированной причины отклонения.

## Compliance Service (External) / Сервис комплаенса (внешний)

> **Архитектурное примечание.** Проверки комплаенса вынесены из основного процесса в
> отдельный внешний сервис. В основной схеме (`Платёжный_процесс_полный.PlantUml`)
> остаётся только вызов сервиса и реакция на его решение; детальная логика проверок
> описана в схеме `Сервис_комплаенса.PlantUml`. Ниже сначала описано взаимодействие с
> сервисом (в основном процессе), затем — внутренние шаги самого сервиса.

### Send Screening Request / Отправка запроса на проверку (основной процесс)

Вызов внешнего сервиса комплаенса: основной процесс делегирует проверки, передавая
данные платежа.

- **Суть.** Точка интеграции с сервисом комплаенса — асинхронный/синхронный вызов
  проверки, а не выполнение проверок внутри казначейской системы.
- **Источник/вход.** Согласованный объект платежа (статус `Approved / Согласован`) с шага
  `Approval Workflow / Процесс согласования`.
- **Что передаётся.** Стороны платежа, сумма, валюта, банковские реквизиты (IBAN/BIC),
  назначение и документ-источник — набор данных, необходимый сервису для скрининга.
- **Результат/выход.** Запрос уходит в `Compliance Service (External)`; ожидается ответ на
  шаге `Receive Compliance Decision / Получение решения комплаенса`.
- **Роль (RACI).** Казначейство / система TRM — R (формирует и отправляет запрос);
  сервис комплаенса — исполнитель проверок.
- **Ключевые атрибуты.** Идентификатор запроса, состав переданных данных, канал/интерфейс
  вызова, метка времени.

### Receive Compliance Decision / Получение решения комплаенса (основной процесс)

Приём решения от внешнего сервиса и передача его в развилку реакции.

- **Суть.** Основной процесс получает агрегированное решение сервиса (`Passed` / `Failed`
  с причинами) и на его основе принимает бизнес-решение.
- **Источник/вход.** Ответ сервиса `Compliance Service (External)` на ранее отправленный запрос.
- **Результат/выход.** Решение передаётся в развилку `Compliance passed? / Комплаенс пройден?`
  (обрабатывается в партиции `Treasury & Risk Management`).
- **Роль (RACI).** Казначейство / система TRM — R (принимает и обрабатывает ответ);
  комплаенс-офицер — A (по эскалациям).
- **Ключевые атрибуты.** Итоговое решение, причины/коды срабатываний, ссылки на детали
  проверок, метка времени, тайм-аут/повтор при отсутствии ответа.
- **Типичные ошибки/риски.** Отсутствие ответа сервиса (таймаут), рассинхрон статусов,
  потеря контекста запроса, обработка устаревшего решения.

## Внутренние шаги сервиса (Сервис_комплаенса.PlantUml)

### Sanctions List Screening / Проверка по санкционным спискам

Первый шаг внутри сервиса комплаенса: проверка участников платежа по санкционным и
«стоп»-спискам до его исполнения. Обязательный регуляторный контроль в казначействе.

- **Суть.** Скрининг контрагента и связанных сторон платежа против санкционных перечней,
  чтобы не допустить платёж в адрес запрещённого лица/юрисдикции.
- **Источник/вход.** Данные платежа из входящего запроса сервиса
  (`Receive Screening Request`), инициированного шагом `Send Screening Request` основного процесса.
- **Что проверяется (типовое в SAP).**
  - Стороны: получатель, банк получателя, банки-посредники, при необходимости — конечный бенефициар.
  - Списки: OFAC (SDN), EU, UN, HMT/OFSI, локальные перечни ЦБ/регуляторов.
  - Реквизиты: наименование, адрес, страна, BIC/банк, ключевые слова назначения платежа.
  - Технология: нечёткое сопоставление (fuzzy matching), контроль запрещённых юрисдикций.
  - Интеграция: SAP Watch List Screening (GTS) или внешний провайдер скрининга.
- **Результат/выход.** При отсутствии совпадений — переход к `AML Check / Проверка AML`.
  При совпадении (hit) — эскалация в общий контроль комплаенса
  (`Compliance passed? / Комплаенс пройден?` → `Hold & Investigate`).
- **Роль (RACI).** Комплаенс-офицер — R/A (исполняет и отвечает);
  казначей — I (информируется), санкционный/юридический эксперт — C.
- **Ключевые атрибуты.** Использованные списки и их версия/дата, результат (чисто/совпадение),
  оценка совпадения (score), проверенные стороны, метка времени, решение по hit.
- **Статус.** Промежуточный контроль в рамках перехода к `Compliant / Комплаенс пройден`;
  при подтверждённом совпадении ведёт к терминальному `Compliance Rejected / Отклонён комплаенсом`.
- **Типичные ошибки/риски.** Ложные срабатывания (false positive) и их избыточная доля,
  пропуск совпадения (false negative), устаревшие версии списков, неполный набор
  проверяемых сторон, отсутствие аудита решений по совпадениям.

### AML Check / Проверка AML (ПОД/ФТ)

Второй шаг комплаенса: контроль на противодействие отмыванию доходов и финансированию
терроризма (ПОД/ФТ). В отличие от санкционного скрининга «по спискам», здесь оценивается
характер и риск самой операции.

- **Суть.** Оценка платежа на признаки подозрительной активности и соответствие
  риск-профилю контрагента, чтобы предотвратить использование платежа в схемах
  отмывания/финансирования терроризма.
- **Источник/вход.** Объект платежа, прошедший `Sanctions List Screening / Проверка по
  санкционным спискам` (совпадений нет).
- **Что проверяется (типовое).**
  - Профиль риска контрагента (KYC/CDD), статус PEP (публичные должностные лица).
  - Поведенческие правила и сценарии: необычные суммы, частота, дробление (structuring),
    отклонение от типового профиля.
  - Юрисдикции повышенного риска, транзит через рисковые страны/банки.
  - Назначение платежа и экономический смысл операции.
  - Интеграция: специализированная AML-система/провайдер, риск-скоринг.
- **Результат/выход.** При приемлемом риске — переход к `Duplicate Payment Check / Контроль
  дублей платежей`. При срабатывании правил — эскалация в общий контроль
  (`Compliance passed?` → `Hold & Investigate`), при необходимости — формирование SAR/STR
  (сообщение о подозрительной операции).
- **Роль (RACI).** Комплаенс-офицер / AML-аналитик — R/A;
  казначей — I; юридический/риск-эксперт — C.
- **Ключевые атрибуты.** Риск-скор операции, сработавшие сценарии/правила, статус KYC/PEP,
  решение (пропустить/эскалировать), признак формирования SAR/STR, метка времени.
- **Статус.** Промежуточный контроль на пути к `Compliant / Комплаенс пройден`;
  при подтверждённом риске ведёт к терминальному `Compliance Rejected / Отклонён комплаенсом`.
- **Типичные ошибки/риски.** Устаревшие данные KYC, неоткалиброванные сценарии (много
  ложных срабатываний или пропуски), необнаруженный structuring, отсутствие аудита
  и своевременного SAR/STR, «ручные» исключения без обоснования.

### Duplicate Payment Check / Контроль дублей платежей

Третий шаг комплаенса: проверка на повторную оплату по существу — не платим ли мы дважды
за одно и то же обязательство. Это бизнес-контроль дублей, в отличие от технического
контроля на шаге `Validate Request`.

- **Суть.** Предотвращение повторного платежа даже тогда, когда заявки формально разные,
  созданы из разных источников или в разное время. Финальный барьер перед оплатой.
- **Источник/вход.** Объект платежа, прошедший `AML Check / Проверка AML (ПОД/ФТ)`.
- **Что проверяется (типовое в SAP).**
  - Совпадение бизнес-признаков: получатель + сумма + валюта + номер счёта/инвойса.
  - Скользящее окно (например, платежи за N дней) и «похожие» платежи (fuzzy).
  - Уже исполненные и находящиеся в обработке платежи (в т.ч. в предложениях/поручениях).
  - Стандартный контроль дублей кредиторских счетов SAP (проверка по ссылке/reference).
- **Отличие от контроля дублей в `Validate Request`.** Там — *технический* дубль заявки
  (повторный импорт одного документа/IDoc, идемпотентность приёма). Здесь — *бизнес*-дубль
  платежа по существу (одно и то же обязательство оплачивается повторно).
- **Результат/выход.** При отсутствии дублей — переход к развилке
  `Compliance passed? / Комплаенс пройден?` и далее `Set Status: Compliant`.
  При обнаружении дубля — `Hold & Investigate (Compliance)` и разбор.
- **Роль (RACI).** Комплаенс-офицер / казначей — R; руководитель казначейства — A;
  бухгалтерия (AP) — C.
- **Ключевые атрибуты.** Набор признаков сравнения, размер окна, найденные кандидаты-дубли,
  оценка схожести, решение (пропустить/удержать), метка времени.
- **Статус.** Промежуточный контроль на пути к `Compliant / Комплаенс пройден`;
  подтверждённый дубль ведёт к удержанию и возможной отмене платежа.
- **Типичные ошибки/риски.** Пропуск дубля из-за расхождений в реквизитах (разный формат
  инвойса), слишком узкое окно сравнения, избыточные ложные срабатывания, ручное снятие
  блокировки без проверки, дубли между разными системами-источниками.

### Compliance passed? / Комплаенс пройден? (развилка и обработка результата)

> Выполняется в основном процессе (партиция `Treasury & Risk Management`), а не в сервисе:
> сервис лишь возвращает решение, а реакцию на него — удержание, расследование, отмену —
> отрабатывает казначейство.

Итоговая развилка обработки решения комплаенса: по решению сервиса (агрегат санкционного
скрининга, AML и контроля дублей) принимается решение — пропустить платёж дальше или удержать.
Включает шаги `Set Status: Compliant`, `Hold & Investigate` и вложенную развилку
`Cleared after investigation?`.

- **Суть.** Единая точка бизнес-реакции на комплаенс-решение: определяет дальнейший маршрут платежа.
- **Источник/вход.** Решение сервиса, полученное на шаге
  `Receive Compliance Decision / Получение решения комплаенса` (агрегат `Sanctions List
  Screening`, `AML Check`, `Duplicate Payment Check`).
- **Ветви развилки.**
  - `Yes / Да` (все проверки чисто) → `Set Status: Compliant / Статус: Комплаенс пройден`,
    объект переходит в партицию `Cash Management`.
  - `No / Нет` (есть срабатывание) → `Hold & Investigate (Compliance) / Блокировка и
    расследование (комплаенс)`, затем вложенная развилка
    `Cleared after investigation? / Снято после расследования?`:
    - `Yes / Да` → платёж реабилитирован, продолжает движение по процессу;
    - `No / Нет` → `Cancel Payment (Status: Compliance Rejected) / Отмена платежа
      (Статус: Отклонён комплаенсом)`, завершение процесса.
- **Связанные шаги.**
  - `Set Status: Compliant` — фиксация успешного прохождения комплаенса как статуса объекта.
  - `Hold & Investigate` — временное удержание с ручным разбором совпадения/срабатывания
    (документирование решения, привлечение экспертов).
  - `Cleared after investigation?` — результат расследования: ложное срабатывание снимается,
    подтверждённое нарушение ведёт к отмене.
- **Результат/выход.** Либо `Compliant / Комплаенс пройден` и переход к `Cash Management`,
  либо терминальный `Compliance Rejected / Отклонён комплаенсом`.
- **Роль (RACI).** Комплаенс-офицер — A (принимает решение); AML/санкционный аналитик — R;
  казначей — I; юридический эксперт — C.
- **Ключевые атрибуты.** Сводный результат проверок, основание удержания, ход и итог
  расследования, обоснование снятия/отклонения, ответственный, метки времени (для аудита).
- **Статус.** `Compliant / Комплаенс пройден` при успехе; `Compliance Rejected /
  Отклонён комплаенсом` при подтверждённом нарушении.
- **Типичные ошибки/риски.** Снятие удержания без должного обоснования, затягивание
  расследования (просрочка платежа), отсутствие аудиторского следа по решению,
  конфликт интересов (решение принимает заинтересованное лицо).

## Cash Management (Управление денежными средствами) — ликвидность

### Calculate Cash Position / Расчёт денежной позиции

Определение текущего фактического остатка денежных средств перед платежом.

- **Суть.** Расчёт актуальной денежной позиции по банковским счетам на дату/момент,
  чтобы понимать доступные средства для оплаты.
- **Источник/вход.** Прошедший комплаенс объект платежа (`Compliant / Комплаенс пройден`),
  а также остатки и обороты по счетам (банковские выписки, внутренние проводки).
- **Что учитывается (типовое в SAP).** Остатки house bank/банковских счетов, подтверждённые
  и ожидаемые поступления/списания, memo records, данные Cash Management (`FF7A/FF7B`).
- **Результат/выход.** Рассчитанная позиция передаётся в `Run Liquidity Forecast`.
- **Роль (RACI).** Кэш-менеджер — R (исполнитель); казначей — I (информируется).
- **Ключевые атрибуты.** Дата/момент расчёта, счета в составе позиции, валюта,
  доступный остаток, источники данных.
- **Статус.** Промежуточный шаг; статус объекта — `Compliant / Комплаенс пройден`.
- **Типичные ошибки/риски.** Неполный охват счетов, устаревшие/незагруженные выписки,
  двойной учёт операций, некорректная дата валютирования.

### Run Liquidity Forecast / Прогноз ликвидности

Прогнозирование будущих денежных потоков для оценки достаточности средств.

- **Суть.** Построение прогноза притоков/оттоков на горизонт планирования, чтобы оценить,
  хватит ли ликвидности на исполнение платежа с учётом других обязательств.
- **Источник/вход.** Денежная позиция с шага `Calculate Cash Position`, планируемые платежи,
  поступления, договорные и казначейские потоки.
- **Что учитывается (типовое в SAP).** Liquidity Forecast (`FF7B`), плановые позиции,
  открытые обязательства AP/AR, казначейские сделки, лимиты и кредитные линии.
- **Результат/выход.** Прогноз передаётся в развилку `Enough Liquidity? / Достаточно
  ликвидности?`.
- **Роль (RACI).** Кэш-менеджер — R; казначей — I.
- **Ключевые атрибуты.** Горизонт прогноза, статьи притоков/оттоков, прогнозный остаток,
  сценарии, дата расчёта.
- **Статус.** Промежуточный шаг; статус объекта — `Compliant / Комплаенс пройден`.
- **Типичные ошибки/риски.** Неучтённые крупные оттоки, оптимистичные допущения по
  поступлениям, ошибки горизонта/сценариев, игнорирование блокировок средств.

### Enough Liquidity? / Достаточно ликвидности? (развилка и обработка)

Развилка проверки достаточности средств с циклом урегулирования нехватки ликвидности.
Включает шаги `Payment Block`, `Escalate / Raise Financing / Reschedule Payment`,
`Cancel Payment (No Liquidity)` и условие цикла `Liquidity resolved?`.

- **Суть.** Решение о возможности оплаты по критерию наличия средств; при нехватке —
  не тупик, а цикл урегулирования.
- **Источник/вход.** Прогноз с шага `Run Liquidity Forecast`.
- **Ветви развилки.**
  - `Yes / Да` (средств достаточно) → выход из цикла, переход в `Payment Factory`;
    объект получает статус `Funded / Обеспечен ликвидностью`.
  - `No / Нет` (нехватка) → `Payment Block / Блокировка платежа`, затем развилка
    `Resolution possible? / Возможно урегулирование?`:
    - `Yes / Да` → `Escalate / Raise Financing / Reschedule Payment` (эскалация,
      привлечение финансирования, перенос даты) и повторная проверка (цикл
      `repeat while Liquidity resolved?`);
    - `No / Нет` → `Cancel Payment (Status: No Liquidity) / Отмена платежа
      (Статус: Нет ликвидности)`, завершение процесса.
- **Результат/выход.** Либо обеспеченный ликвидностью платёж (`Funded`) и переход к
  формированию платёжного предложения, либо терминальный `Cancelled (No Liquidity)`.
- **Роль (RACI).** Кэш-менеджер — R (оценка, урегулирование); казначей / руководитель
  казначейства — A (решение об эскалации/финансировании).
- **Ключевые атрибуты.** Признак достаточности, сумма дефицита, способ урегулирования,
  новая дата платежа, решение, метки времени.
- **Статус.** `Funded / Обеспечен ликвидностью` при успехе; `Cancelled (No Liquidity) /
  Отменён (нет ликвидности)` при невозможности урегулирования.
- **Типичные ошибки/риски.** Затягивание урегулирования (просрочка), необоснованное снятие
  блокировки, зацикливание без результата, некорректная оценка дефицита.

## Payment Factory (Платёжная фабрика)

### Create Payment Proposal / Создание платёжного предложения

Формирование платёжного предложения (какие платежи, каким счётом/банком, когда).

- **Суть.** Подготовка предложения к оплате — группировка и параметризация платежей перед
  формированием поручения. Открывает цикл `repeat` «создание → проверка предложения».
- **Источник/вход.** Обеспеченный ликвидностью платёж (`Funded`) из `Cash Management`.
- **Что формируется (типовое в SAP).** Платёжное предложение (аналог proposal в `F110`):
  выбор открытых позиций, house bank/счёт, способ оплаты, дата платежа, группировка/неттинг.
- **Результат/выход.** Предложение передаётся на шаг `Review Proposal`.
- **Роль (RACI).** Оператор платежей (Payment Factory) — R.
- **Ключевые атрибуты.** Состав платежей, house bank/счёт, способ оплаты, дата, суммы,
  признаки группировки.
- **Статус.** Объект переходит в `Proposed / В предложении`.
- **Типичные ошибки/риски.** Неверный выбор счёта/способа оплаты, ошибочная группировка,
  включение неоплачиваемых/заблокированных позиций.

### Review Proposal / Проверка предложения (с развилкой Proposal approved?)

Контроль платёжного предложения перед формированием поручения; при необходимости —
корректировка или отклонение (цикл).

- **Суть.** Проверка корректности и полноты предложения; барьер перед необратимым
  формированием платёжного поручения.
- **Источник/вход.** Предложение с шага `Create Payment Proposal`.
- **Ветви развилки `Proposal approved? / Предложение утверждено?`.**
  - `Yes / Да` → выход из цикла, переход к `Generate Payment Order`.
  - `No / Нет` → `Adjust / Reject Proposal / Корректировка / отклонение предложения` и
    повторное создание/проверка предложения (петля цикла).
- **Результат/выход.** Утверждённое предложение направляется на `Generate Payment Order`.
- **Роль (RACI).** Оператор платежей — R; при существенных корректировках возможна
  консультация казначея (C).
- **Ключевые атрибуты.** Результат проверки, внесённые корректировки, причина отклонения,
  ответственный, метки времени.
- **Статус.** Остаётся `Proposed / В предложении` до формирования поручения.
- **Типичные ошибки/риски.** Формальная проверка без контроля сути, повторные корректировки
  без результата, пропуск ошибок в реквизитах/суммах.

### Generate Payment Order / Формирование платёжного поручения

Создание платёжного поручения на основе утверждённого предложения.

- **Суть.** Материализация утверждённого предложения в платёжное поручение — основание для
  формирования платёжного файла в банк.
- **Источник/вход.** Утверждённое предложение с шага `Review Proposal`.
- **Что формируется (типовое в SAP).** Платёжный документ/поручение (payment document `F110`),
  проводки, назначение платежа, привязка к house bank/счёту.
- **Результат/выход.** Поручение передаётся в партицию `Bank Communication Management`.
- **Роль (RACI).** Оператор платежей — R.
- **Ключевые атрибуты.** Номер поручения, сумма, валюта, получатель, счёт, дата платежа,
  ссылка на предложение.
- **Статус.** Объект переходит в `Ordered / Поручение сформировано`.
- **Типичные ошибки/риски.** Расхождение поручения с предложением, ошибки проводок,
  некорректная дата/счёт.

## Bank Communication Management (Управление банковскими коммуникациями)

### Generate ISO20022 XML / Формирование XML ISO20022

Формирование платёжного файла в стандарте ISO 20022 (pain.001).

- **Суть.** Преобразование платёжного поручения в стандартизованный банковский формат
  (обычно `pain.001`) для передачи в банк.
- **Источник/вход.** Платёжное поручение с шага `Generate Payment Order` (`Ordered`).
- **Что формируется (типовое в SAP).** XML-сообщение `pain.001` (кредитовый перевод),
  структурированное по требованиям банка/схемы (SEPA, SWIFT и т.п.).
- **Результат/выход.** Файл передаётся на шаг `Sign & Encrypt Payment File`.
- **Роль (RACI).** Администратор BCM — R.
- **Ключевые атрибуты.** Формат/версия схемы, идентификатор файла и сообщений, количество и
  сумма платежей, реквизиты сторон.
- **Статус.** Промежуточный шаг; статус объекта — `Ordered / Поручение сформировано`.
- **Типичные ошибки/риски.** Несоответствие формату/версии банка, ошибки маппинга полей,
  некорректная кодировка, нарушение лимитов на размер файла.

### Sign & Encrypt Payment File / Подписание и шифрование платёжного файла

Криптографическая защита платёжного файла перед отправкой.

- **Суть.** Наложение электронной подписи и шифрование файла для обеспечения целостности,
  подлинности и конфиденциальности при передаче в банк.
- **Источник/вход.** Сформированный XML-файл с шага `Generate ISO20022 XML`.
- **Как выполняется (типовое в SAP).** Подпись сертификатом (по требованиям банка),
  шифрование (например, через SAP Cryptographic Library / внешний HSM), принцип «четырёх глаз»
  для авторизации отправки.
- **Результат/выход.** Подписанный/зашифрованный файл передаётся на `Transmit Payment File`.
- **Роль (RACI).** Администратор BCM — R; уполномоченные подписанты — A.
- **Ключевые атрибуты.** Сертификат/ключ, алгоритм подписи и шифрования, подписанты,
  метки времени, хэш файла.
- **Типичные ошибки/риски.** Просроченные/отозванные сертификаты, ошибки конфигурации ключей,
  обход принципа «четырёх глаз», компрометация ключевого материала.

### Transmit Payment File / Передача платёжного файла

Отправка защищённого файла в банк по согласованному каналу.

- **Суть.** Доставка платёжного файла в банк через установленный канал связи.
- **Источник/вход.** Подписанный/зашифрованный файл с шага `Sign & Encrypt Payment File`.
- **Как выполняется (типовое в SAP).** Каналы SWIFT (FIN/FileAct), EBICS, host-to-host,
  банковские шлюзы; отправка через SAP Bank Communication Management / Multi-Bank Connectivity.
- **Результат/выход.** После передачи ожидается квитанция на шаге
  `Receive Bank Acknowledgement (pain.002)`.
- **Роль (RACI).** Администратор BCM — R.
- **Ключевые атрибуты.** Канал передачи, идентификатор сессии/сообщения, статус отправки,
  метки времени, признак повтора.
- **Статус.** Объект переходит в `Transmitted / Передан в банк`.
- **Типичные ошибки/риски.** Сбой канала, отсутствие подтверждения доставки, повторная
  отправка (дубли), тайм-аут соединения.

### Receive Bank Acknowledgement (pain.002) / Получение квитанции банка (с развилкой)

Приём статусной квитанции банка и проверка приёма файла. Включает развилку
`Bank accepted file?` и шаг `Handle Rejection & Resubmit File`.

- **Суть.** Получение технического/бизнес-статуса от банка (`pain.002`) о приёме или
  отклонении платёжного файла — подтверждение, что банк принял файл в обработку.
- **Источник/вход.** Ответ банка на переданный файл (`Transmitted`).
- **Ветви развилки `Bank accepted file? / Банк принял файл?`.**
  - `Yes / Да` → переход в партицию `External Bank` (исполнение платежа).
  - `No / Нет` → `Handle Rejection & Resubmit File / Обработка отказа и повторная отправка
    файла`, завершение текущей ветки (после исправления — повторная отправка).
- **Результат/выход.** Принятый файл идёт на исполнение; отклонённый — на обработку отказа.
- **Роль (RACI).** Администратор BCM — R; казначей — I.
- **Ключевые атрибуты.** Код статуса `pain.002`, причины отклонения, идентификатор исходного
  сообщения, метки времени.
- **Статус.** При приёме остаётся `Transmitted / Передан в банк`; при отказе — обработка/повтор.
- **Типичные ошибки/риски.** Игнорирование квитанции, неверная интерпретация кодов статуса,
  отсутствие обработки частичных отказов, повторная отправка без исправления причины.

## External Bank (Внешний банк)

### Payment executed? / Платёж исполнен? (развилка) и обработка результата

Развилка результата исполнения платежа банком. Включает шаги `Execute Payment`,
`Payment Rejected / Returned by Bank`, `Notify Treasury & Investigate`.

- **Суть.** Отражение фактического результата обработки платежа во внешнем банке —
  исполнение либо отказ/возврат.
- **Источник/вход.** Принятый банком платёжный файл (после `Bank accepted file? = Yes`).
- **Ветви развилки `Payment executed? / Платёж исполнен?`.**
  - `Yes / Да` → `Execute Payment / Исполнение платежа` (средства списаны/переведены).
  - `No / Нет` → `Payment Rejected / Returned by Bank / Платёж отклонён / возвращён банком`,
    затем `Notify Treasury & Investigate / Уведомление казначейства и разбор причины`.
- **Результат/выход.** В обоих случаях далее следует `Return Bank Statement` (выписка отразит
  исполнение или возврат).
- **Роль (RACI).** Внешний банк — исполнитель; казначейство — I (получает уведомление) и
  инициирует разбор при отказе/возврате.
- **Ключевые атрибуты.** Статус исполнения, причина отказа/возврата, дата валютирования,
  сумма, референс банка.
- **Статус.** При успехе — `Executed / Исполнен`; при отказе/возврате — терминальный/особый
  `Returned by Bank / Возвращён банком`.
- **Типичные ошибки/риски.** Неверные реквизиты получателя, отзыв/возврат платежа,
  расхождение суммы, задержки исполнения.

### Return Bank Statement / Возврат банковской выписки

Формирование и возврат банковской выписки по результатам операций.

- **Суть.** Банк предоставляет выписку, отражающую фактические движения (исполнение, возврат,
  комиссии), — основа для последующей сверки.
- **Источник/вход.** Результат исполнения (или отказа/возврата) на стороне банка.
- **Что формируется (типовое).** Выписка в формате `camt.053` (итоговая), при необходимости
  `camt.052` (интрадей) / `camt.054` (детали по операциям).
- **Результат/выход.** Выписка передаётся в партицию `Cash Management` на шаг `Import Statement`.
- **Роль (RACI).** Внешний банк — исполнитель; кэш-менеджер — I.
- **Ключевые атрибуты.** Формат выписки, период, движения, конечный остаток, референсы операций.
- **Типичные ошибки/риски.** Задержка/неполнота выписки, расхождение форматов, отсутствие
  детализации по операциям.

## Cash Management (Управление денежными средствами) — сверка

### Import Statement / Импорт выписки

Загрузка банковской выписки в систему для сверки.

- **Суть.** Приём и регистрация банковской выписки в казначейской системе для дальнейшего
  сопоставления и сверки.
- **Источник/вход.** Выписка от банка с шага `Return Bank Statement` (`camt.053` и др.).
- **Как выполняется (типовое в SAP).** Импорт электронной банковской выписки
  (Electronic Bank Statement, `FF.5`/`FEBAN`), автоматическая обработка форматов camt/MT940.
- **Результат/выход.** Импортированная выписка передаётся в `Automatic Matching`.
- **Роль (RACI).** Кэш-менеджер — R.
- **Ключевые атрибуты.** Формат, период, количество строк, конечный остаток, статус импорта.
- **Типичные ошибки/риски.** Ошибки формата/парсинга, повторный импорт (дубли),
  пропуск строк, несоответствие остатков.

### Automatic Matching / Автоматическое сопоставление (с развилкой All items matched?)

Автоматическое сопоставление строк выписки с ожидаемыми платежами; обработка
несопоставленных позиций.

- **Суть.** Автоматическая привязка операций выписки к платежам/открытым позициям по правилам;
  сокращает ручной труд при сверке.
- **Источник/вход.** Импортированная выписка с шага `Import Statement`.
- **Ветви развилки `All items matched? / Все позиции сопоставлены?`.**
  - `Yes / Да` → переход к `Reconciliation`.
  - `No / Нет` → `Manual Reconciliation & Clearing / Ручная сверка и клиринг несопоставленных
    позиций`, затем `Reconciliation`.
- **Что учитывается (типовое в SAP).** Правила сопоставления EBS, референсы платежей,
  суммы/даты, интерпретационные алгоритмы, клиринг открытых позиций.
- **Результат/выход.** Сопоставленные (и доведённые вручную) позиции идут в `Reconciliation`.
- **Роль (RACI).** Кэш-менеджер — R; бухгалтерия — C (по спорным позициям).
- **Ключевые атрибуты.** Доля автосопоставления, число исключений, правила, причины
  несопоставления, ответственный.
- **Типичные ошибки/риски.** Низкая доля автоматизации, ошибочные сопоставления,
  «зависшие» несопоставленные позиции, отсутствие правил под новые сценарии.

### Reconciliation / Сверка

Итоговая сверка данных банка с учётными данными.

- **Суть.** Подтверждение соответствия банковских движений и учётных записей; фиксация
  клиринга открытых позиций.
- **Источник/вход.** Результаты автоматического и ручного сопоставления.
- **Что выполняется (типовое в SAP).** Клиринг открытых позиций, проводки по счетам,
  подтверждение соответствия остатков.
- **Результат/выход.** Подтверждённые данные идут в `Update Cash Position` и `Update Forecast`.
- **Роль (RACI).** Кэш-менеджер — R; бухгалтерия — C/A по проводкам.
- **Ключевые атрибуты.** Статус сверки, расхождения, проведённые клиринги, дата.
- **Статус.** Объект достигает `Reconciled / Сверен`.
- **Типичные ошибки/риски.** Незакрытые расхождения, ошибочные проводки, отсутствие
  контроля остатков.

### Update Cash Position / Обновление денежной позиции

Актуализация денежной позиции по итогам сверки.

- **Суть.** Обновление фактической денежной позиции после подтверждённых движений и клиринга.
- **Источник/вход.** Результаты `Reconciliation`.
- **Результат/выход.** Обновлённая позиция используется как база для `Update Forecast`.
- **Роль (RACI).** Кэш-менеджер — R; казначей — I.
- **Ключевые атрибуты.** Обновлённые остатки по счетам, дата/момент, источники движений.
- **Типичные ошибки/риски.** Неполное отражение движений, рассинхрон с учётом, устаревшие данные.

### Update Forecast / Обновление прогноза

Актуализация прогноза ликвидности по фактическим данным.

- **Суть.** Корректировка прогноза денежных потоков с учётом фактического исполнения платежа
  и обновлённой позиции — замыкает цикл управления ликвидностью.
- **Источник/вход.** Обновлённая денежная позиция с шага `Update Cash Position`.
- **Результат/выход.** Актуализированный прогноз ликвидности; завершение сквозного процесса.
- **Роль (RACI).** Кэш-менеджер — R; казначей — I.
- **Ключевые атрибуты.** Обновлённый горизонт и статьи прогноза, отклонения план/факт, дата.
- **Статус.** Завершающий шаг процесса; объект платежа — в терминальном `Reconciled / Сверен`.
- **Типичные ошибки/риски.** Неучёт фактического исполнения, сохранение устаревших допущений,
  отсутствие анализа отклонений план/факт.

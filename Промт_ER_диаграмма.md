# Промпт: построение ER-диаграммы

Используй этот промпт для создания или изменения ER-диаграмм в формате PlantUML.

## Цель

Построй ER-диаграмму предметной области на основе предоставленных контрактов, маппингов,
примеров payload и описаний сущностей. Не придумывай реквизиты, связи или кардинальности,
если они не подтверждены входными документами. Неясные решения фиксируй вопросом.

## Формат файла

- Формат: PlantUML, расширение `.PlantUml`.
- Диаграмма начинается с `@startuml` и заканчивается `@enduml`.
- Используй `entity` для таблиц и `skinparam linetype ortho`.
- Отображай имя таблицы на английском и русском:

  ```plantuml
  entity "Payment Request\nЗаявка на оплату" as PaymentRequest {
  }
  ```

## Правила реквизитов

- Обязательный реквизит обозначай `*`.
- Первичный ключ обозначай `<<PK>>`.
- Внешний ключ обозначай явно с таблицей и полем назначения:

  ```plantuml
  originDocumentId : UUID <<FK → Documents.id, optional>>
  ```

- Внешний ключ, который одновременно является первичным ключом, обозначай так:

  ```plantuml
  paymentRequestId : UUID <<PK, FK → PaymentRequest.id>>
  ```

- Уникальность отмечай `<<unique>>`.
- Необязательный реквизит обозначай `<<optional>>`; не ставь перед ним `*`.
- Строковые коды храни как `string`, чтобы не потерять ведущие нули: BUKRS, ИНН, КПП,
  номера документов и позиций.

## Связи и кардинальности

- Связь создавай только между самостоятельными таблицами.
- Если структура является только составным реквизитом и не имеет отдельной таблицы,
  не изображай её отдельной ER-сущностью.
- Используй нотацию PlantUML:
  - `||--||` — обязательная связь один-к-одному;
  - `||--o{` — один-ко-многим;
  - `|o--o{` — ноль-или-один к нулю-или-многим.
- Подписывай связь именем реквизита или её бизнес-смыслом:

  ```plantuml
  Documents |o--o{ PaymentRequest : originDocument
  ```

- Кардинальность должна согласовываться с обязательностью внешнего ключа.

## Справочники

Вынеси в отдельную таблицу коды, которые имеют ограниченный набор допустимых значений
и переиспользуются:

- `CompanyCodes` — коды компаний (`BUKRS`);
- `DocumentTypes` — типы документов;
- `Counterparties` — контрагенты;
- `PaymentMethods` — способы оплаты;
- `PaymentRequestStatuses` — статусы заявок.

Поле-ссылка в основной таблице должно содержать явный внешний ключ, а справочник —
первичный ключ `code` или `id`.

## Идентификаторы и технические поля

- Различай идентификатор бизнес-сущности, идентификатор документа и идентификатор
  конкретной строки документа.
- Не смешивай интеграционный идентификатор со ссылкой на таблицу:
  - `sourceLineItemId` — технический строковый ключ интеграции;
  - `sourceDocumentId <<FK → Documents.id>>` — ссылка на документ-источник;
  - `...Id <<FK → Table.id>>` — ссылка на запись локальной таблицы.
- Для составных канонических ключей добавляй нотацию с правилом формирования и примером.

  ```plantuml
  note right of FiPositionNumber
    lineItemID формируется по правилу:
    FI_POSITION|BUKRS=<companyCode>|...|POSNO=<positionNumber>
  end note
  ```

## Проверка перед завершением

1. У каждой таблицы есть первичный ключ.
2. У каждого внешнего ключа указана таблица и поле назначения.
3. Для каждого справочника есть связь с использующими его таблицами.
4. Нет дублирования одного реквизита в нескольких таблицах без обоснования.
5. Нотации с составными ключами соответствуют полям диаграммы и контракту.
6. Имена полей согласованы с утверждённым контрактом и примерами payload.

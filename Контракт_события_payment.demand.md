# Спецификация логического event contract `payment.demand`

**Статус:** Черновик 0.2  
**Топик Kafka:** `payment.demand`  
**Продюсер:** SAP FI / Финансовый учёт  
**Консьюмер:** Treasury System (TRM) / Казначейская система  
**Назначение:** передача в TRM факта возникновения одной исходящей платёжной потребности.

Документ фиксирует логическую семантику события и не заменяет физическую схему
сериализации. Для валидации в Schema Registry после согласования должна быть создана
отдельная Avro- или JSON Schema.

Точные правила `messageKey`, `eventId` и `sourceDocumentId` определены в
`Спецификация_ключей_событий.md`.

---

## 1. Границы и бизнес-смысл

`payment.demand` сообщает, что в FI возникла конкретная сущность, требующая исходящего
платежа. Одно событие содержит одну потребность и приводит к созданию одной
`Payment Request / Заявка на оплату` в TRM (`1 → 1`).

Объединение уже созданных заявок выполняется позднее внутри казначейской системы и не
входит в ответственность Kafka-события.

Контракт покрывает только **возникновение** потребности. Изменение, отмена, блокировка,
разблокировка и повторная отправка требуют отдельных правил и в этот контракт не входят.

### 1.1. Публикующие сущности FI

| `documentType` | Сущность-источник | Роль в платёжной потребности |
|---|---|---|
| `VENDOR_OPEN_ITEM` | Open Vendor Item (FI-AP) / Открытая позиция кредитора | Обязательство перед поставщиком |
| `CUSTOMER_OPEN_ITEM` | Open Customer Item (FI-AR) / Открытая позиция дебитора | Возврат денежных средств покупателю |
| `TAX` | Taxes / Налоги | Обязательство перед бюджетом |
| `PAYROLL` | Payroll / Зарплата | Выплата по зарплатному реестру |
| `CONTRACT_PAYMENT` | Contract Payment / Платёж по договору | Плановый платёж по договору |
| `MANUAL_REQUEST` | Manual Request / Ручная заявка | Разовая потребность, введённая вручную |

Значение `sourceModule` для текущей версии контракта всегда равно `FI`.

### 1.2. Документы происхождения

MIRO и Credit Note не являются Kafka-продюсерами и не публикуют самостоятельное
`payment.demand`.

| Документ происхождения | FI-сущность, создающая событие | Правило |
|---|---|---|
| Vendor Invoice (MIRO) / Счёт поставщика | `VENDOR_OPEN_ITEM` | Событие создаётся только по FI-AP позиции. MIRO передаётся как происхождение. |
| Credit Note / Кредит-нота | `CUSTOMER_OPEN_ITEM` | Событие создаётся только по FI-AR позиции. Кредит-нота передаётся как происхождение. |

Это правило исключает двойную публикацию одной платёжной потребности.

## 2. Участники и ответственность

| Участник | Ответственность |
|---|---|
| SAP FI | Создать FI-потребность и запись Outbox в одной локальной транзакции. |
| Outbox / Event Publisher | Опубликовать запись Outbox в `payment.demand`; реализация Publisher, Debezium или иного механизма уточняется отдельно. |
| Apache Kafka | Хранить и доставлять события в четыре партиции с семантикой at-least-once. |
| Demand Consumer | Прочитать, валидировать и дедуплицировать событие; передать его в Builder. |
| Payment Request Builder | Создать одну заявку в TRM либо вернуть идемпотентный результат для ранее обработанного события. |

## 3. Идентификаторы и Kafka key

### 3.1. Обязательные идентификаторы

| Поле | Назначение |
|---|---|
| `eventId` | Уникальный идентификатор экземпляра события; применяется для идемпотентности и трассировки. |
| `messageKey` | Kafka key; определяет партицию и порядок сообщений в её пределах. |
| `sourceDocumentId` | Уникальный идентификатор FI-сущности, породившей потребность. |
| `correlationId` | Сквозной идентификатор для поиска операции между FI, Kafka и TRM. |

### 3.2. Правило формирования `messageKey`

Kafka key должен быть составным:

```text
FI|role=<VENDOR|CUSTOMER>|CP=<counterpartyId>|DOCTYPE=<documentType>|
DOCNO=<documentNumber>|BUKRS=<companyCode>|GJAHR=<fiscalYear>
```

- `FI` — фиксированный модуль-публикатор;
- `role` — роль контрагента: минимум `VENDOR` или `CUSTOMER`;
- `CP` — технический идентификатор контрагента или Business Partner, не отображаемое имя;
- `DOCTYPE` — одно из значений таблицы публикующих сущностей;
- `DOCNO` — номер FI-позиции, FI-документа или реестра;
- `BUKRS` — код компании;
- `GJAHR` — финансовый год.

Для FI-документов `BUKRS` и `GJAHR` обязательны, поскольку номер документа не уникален
без этого контекста. `messageKey` определяет партицию по формуле
`partition = hash(key) % 4`.

Примеры:

```text
FI|role=VENDOR|CP=0001007788|DOCTYPE=VENDOR_OPEN_ITEM|DOCNO=1900012345|BUKRS=1000|GJAHR=2026
FI|role=CUSTOMER|CP=0002003344|DOCTYPE=CUSTOMER_OPEN_ITEM|DOCNO=1800012345|BUKRS=1000|GJAHR=2026
```

### 3.3. `eventId`, `sourceDocumentId` и `correlationId`

- `sourceDocumentId` идентифицирует FI-сущность и в текущей версии равен каноническому
  `messageKey`; точный формат определён в `Спецификация_ключей_событий.md`.
- `eventId` идентифицирует конкретный экземпляр публикации; его точный формат
  (UUID или иной формат) ещё не согласован.
- `correlationId` связывает обработку в FI, Kafka и TRM; правило его формирования ещё
  не согласовано.

`eventId` не заменяет Kafka key: даже при одинаковом ключе возможны повторные публикации,
которые консьюмер обязан обработать идемпотентно.

## 4. Логическая структура события

### 4.1. Метаданные

| Поле | Обяз. | Описание |
|---|---:|---|
| `eventId` | Да | Уникальный ID экземпляра публикации. |
| `eventType` | Да | Фиксированное значение `payment.demand`. |
| `eventVersion` | Да | Версия логического/физического контракта. |
| `occurredAt` | Да | Дата и время возникновения FI-потребности. |
| `publishedAt` | Да | Дата и время публикации из Outbox. |
| `correlationId` | Да | Сквозной идентификатор операции. |
| `producerSystem` | Да | Идентификатор SAP FI или сервиса-публикатора. |

### 4.2. Источник потребности

| Поле | Обяз. | Описание |
|---|---:|---|
| `sourceModule` | Да | Фиксированное значение `FI`. |
| `documentType` | Да | Тип FI-сущности из таблицы в разделе 1.1. |
| `documentNumber` | Да | Номер FI-позиции, FI-документа или реестра. |
| `companyCode` | Да | Код компании (`BUKRS`). |
| `fiscalYear` | Да | Финансовый год (`GJAHR`). |
| `sourceDocumentId` | Да | Уникальный составной ID источника. |
| `sourceDocumentReference` | Да | Техническая ссылка, по которой сущность открывается в FI; формат требует согласования. |

### 4.3. Документ происхождения

Блок передаётся, когда FI-потребность создана внешним для FI документом.

| Поле | Обяз. | Описание |
|---|---:|---|
| `originDocumentType` | Условно | Например, `MIRO` или `CREDIT_NOTE`. |
| `originDocumentNumber` | Условно | Номер документа происхождения. |
| `originModule` | Условно | `MM` для MIRO или `SD`/`FI` для кредит-ноты. |

Для прямых FI-потребностей этот блок не заполняется.

### 4.4. Контрагент и получатель

| Поле | Обяз. | Описание |
|---|---:|---|
| `counterpartyRole` | Да | Минимально `VENDOR` или `CUSTOMER`; для налогов, зарплаты и иных сценариев справочник требует согласования. |
| `counterpartyId` | Да | Технический ID контрагента или Business Partner. |
| `counterpartyName` | Да | Отображаемое наименование; не используется в key. |
| `paymentRecipientId` | Условно | Технический ID фактического получателя. |
| `paymentRecipientName` | Условно | Наименование фактического получателя. |

### 4.5. Данные платёжной потребности

| Поле | Обяз. | Описание |
|---|---:|---|
| `amount` | Да | Сумма потребности; больше нуля. |
| `currency` | Да | Код валюты ISO 4217. |
| `dueDate` | Да | Плановая дата оплаты. |
| `paymentPurpose` | Да | Назначение или экономическое основание платежа. |
| `paymentMethod` | Условно | Способ оплаты; справочник и обязательность не согласованы. |
| `priority` | Условно | Приоритет/срочность; справочник и обязательность не согласованы. |
| `contractReference` | Условно | Ссылка на договор, если применимо. |

### 4.6. Банковские реквизиты

| Поле | Обяз. | Описание |
|---|---:|---|
| `recipientBankAccount` | Условно | Счёт получателя. |
| `recipientBankIban` | Условно | IBAN, если применим. |
| `recipientBankBic` | Условно | BIC, если применим. |

Передача банковских реквизитов допускается только после утверждения требований к защите
данных: доступам к топику, шифрованию и маскированию логов.

---

## 5. Обработка события

1. В FI создаётся одна публикующая сущность из раздела 1.1.
2. В той же локальной транзакции создаётся соответствующая запись Outbox.
3. Publisher или Debezium публикует сообщение в `payment.demand`.
4. Kafka направляет его в одну из четырёх партиций по `messageKey`.
5. `Demand Consumer` валидирует структуру и проверяет повторную обработку по `eventId`.
6. `Payment Request Builder` создаёт одну `Payment Request` со статусом
   `Created / Создан`.
7. Заявка переходит в дальнейший платёжный процесс TRM.

---

## 6. Ошибки и обработка исключений

| Ситуация | Требуемое поведение |
|---|---|
| Сообщение не соответствует физической схеме | Не обрабатывать; после классификации ошибки направить в DLQ. |
| Не заполнено обязательное поле | Не создавать заявку; направить в DLQ с причиной. |
| Неизвестный `documentType` | Не обрабатывать; направить на разбор. |
| Повторный `eventId` | Не создавать дубликат заявки; вернуть/зафиксировать идемпотентный результат. |
| Временная ошибка TRM | Повторить обработку; после исчерпания политики retry направить в DLQ. |

Число повторов, интервалы, владелец DLQ и процедура reprocess должны быть утверждены
отдельной спецификацией Consumer/DLQ.

---

## 7. Открытые решения

Перед созданием физической Avro/JSON Schema необходимо утвердить:

1. Формат `eventId` и `correlationId`.
2. Точный формат `sourceDocumentReference`.
3. Полные справочники ролей контрагентов, способов оплаты и приоритетов.
4. Правила `DOCNO` для `TAX`, `PAYROLL`, `CONTRACT_PAYMENT` и `MANUAL_REQUEST`.
5. Обязательность и правила защиты банковских реквизитов.
6. Выбор механизма публикации: Polling Publisher, Debezium или иной вариант.
7. Политику retry, DLQ, мониторинга и повторной обработки.
8. Контракты для изменений, отмен, блокировок и разблокировок потребностей.
9. Политику версионирования и совместимости Schema Registry.
10. Правила последующего объединения заявок внутри TRM.

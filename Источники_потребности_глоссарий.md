# Глоссарий: источники входящей потребности в заявке на оплату

Справочник по элементам схемы `Источники_потребности_сущности.PlantUml`
(диаграмма классов: системы-источники, их сущности и связь с казначейской системой).

Схема показывает **структурную связь**, а не процесс: в нескольких системах существует
множество сущностей, каждая из которых может породить входящую потребность в оплате,
формализуемую в единый объект `Payment Request / Заявка на оплату` в казначейской системе.

Кардинальность связей: **многие источники → одна заявка** (`* → 1`).

Каждая сущность описывается по единой структуре: суть, когда возникает, типовой объект/
транзакция SAP, ключевые атрибуты, связь с заявкой на оплату.

---

## SAP ERP

Операционная система-источник потребностей. Сгруппирована по функциональным модулям
(MM, SD/FI, FI, TRM). Ниже — сущности каждого модуля.

---

## MM — Procurement / Закупки

Потребности, возникающие в процессе закупок товаров и услуг (расчёты с поставщиками).

### Vendor Invoice (MIRO) / Счёт поставщика (MIRO)

- **Суть.** Проведённый счёт поставщика (входящая фактура) — обязательство оплатить
  поставленные товары/услуги.
- **Когда возникает.** После проверки и проводки входящего счёта (сверка с заказом на
  закупку и приёмкой — three-way match).
- **Типовой объект/транзакция SAP.** Логистический ввод счёта `MIRO`; документ кредитора
  в FI-AP.
- **Ключевые атрибуты.** Поставщик, сумма, валюта, срок оплаты (payment terms), ссылка на
  заказ на закупку (PO), налоги.
- **Связь с заявкой.** Порождает потребность → входит в состав одной заявки на оплату (`* → 1`).

### Open Vendor Item (FI-AP) / Открытая позиция кредитора

- **Суть.** Открытая (неоплаченная) позиция по счёту кредитора в бухгалтерии кредиторов.
- **Когда возникает.** При наличии непогашенного обязательства перед поставщиком
  (в т.ч. созданного вручную в FI, без логистики).
- **Типовой объект/транзакция SAP.** Открытые позиции FI-AP (`FBL1N`), платёжная программа `F110`.
- **Ключевые атрибуты.** Кредитор, сумма, валюта, срок оплаты, дата базовой линии (baseline date),
  блокировки платежа.
- **Связь с заявкой.** Открытая позиция — прямой источник потребности в оплате (`* → 1`).

## SD / FI — Receivables / Расчёты с покупателями

Потребности в выплатах, связанные с покупателями (когда платит компания, а не покупатель).

### Customer Refund / Возврат покупателю

- **Суть.** Возврат денежных средств покупателю (переплата, возврат товара, отмена заказа).
- **Когда возникает.** При образовании обязательства выплатить покупателю (кредитовое сальдо
  по дебитору).
- **Типовой объект/транзакция SAP.** Открытая позиция дебитора с кредитовым сальдо (FI-AR),
  инициирование выплаты через `F110`.
- **Ключевые атрибуты.** Покупатель, сумма, валюта, основание возврата, срок.
- **Связь с заявкой.** Формирует потребность в исходящем платеже покупателю (`* → 1`).

### Credit Note / Кредит-нота

- **Суть.** Кредитовый документ в пользу покупателя (скидка, корректировка, компенсация),
  который может привести к выплате.
- **Когда возникает.** При выставлении кредит-ноты, не закрываемой встречными поставками.
- **Типовой объект/транзакция SAP.** Кредит-нота SD/FI, кредитовая позиция дебитора.
- **Ключевые атрибуты.** Покупатель, сумма, валюта, причина/основание, ссылка на исходный документ.
- **Связь с заявкой.** При выплате остатка порождает потребность в оплате (`* → 1`).

### Down Payment / Аванс

- **Суть.** Авансовый платёж (например, поставщику по договору) как отдельная потребность в оплате.
- **Когда возникает.** По условиям договора/графику авансирования до поставки.
- **Типовой объект/транзакция SAP.** Запрос аванса (down payment request), специальные ГК-проводки
  (special G/L), `F-47`/`F110`.
- **Ключевые атрибуты.** Контрагент, сумма аванса, валюта, срок, ссылка на договор/заказ.
- **Связь с заявкой.** Аванс формирует самостоятельную потребность в оплате (`* → 1`).

## FI — Financial Accounting / Финансовый учёт

Потребности, возникающие напрямую в финансовом учёте, вне логистических процессов.

### Taxes / Налоги

- **Суть.** Обязательства по уплате налогов и сборов в бюджет.
- **Когда возникает.** По результатам расчёта налогов и наступлению сроков уплаты.
- **Типовой объект/транзакция SAP.** Налоговые проводки/обязательства в FI, платёж через `F110`
  или ручную заявку.
- **Ключевые атрибуты.** Вид налога, сумма, валюта, получатель (бюджет/ФНС), срок уплаты.
- **Связь с заявкой.** Налоговое обязательство → потребность в оплате (`* → 1`).

### Payroll / Зарплата

- **Суть.** Обязательства по выплате заработной платы и связанных платежей персоналу.
- **Когда возникает.** По итогам расчёта зарплаты за период.
- **Типовой объект/транзакция SAP.** Результаты HR/Payroll, проводки в FI, платёжная выгрузка.
- **Ключевые атрибуты.** Период, сумма/реестр, валюта, получатели (сотрудники), срок выплаты.
- **Связь с заявкой.** Формирует потребность (обычно реестровую/массовую) в оплате (`* → 1`).

### Contract Payment / Платёж по договору

- **Суть.** Плановые платежи по договорам (аренда, услуги, лизинг, регулярные обязательства).
- **Когда возникает.** По графику платежей/наступлению срока по договору.
- **Типовой объект/транзакция SAP.** Плановые/повторяющиеся проводки, обязательства FI.
- **Ключевые атрибуты.** Контрагент, сумма, валюта, срок, ссылка на договор, периодичность.
- **Связь с заявкой.** Каждый плановый платёж → потребность в оплате (`* → 1`).

### Manual Request / Ручная заявка

- **Суть.** Заявка на оплату, созданная вручную пользователем вне автоматических источников.
- **Когда возникает.** При разовых/нестандартных платежах, не порождённых документами системы.
- **Типовой объект/транзакция SAP.** Ручной ввод платёжной заявки/запроса.
- **Ключевые атрибуты.** Инициатор, контрагент, сумма, валюта, срок, обоснование.
- **Связь с заявкой.** Прямой ручной источник потребности (`* → 1`); требует усиленного контроля.

## TRM Deals / Казначейские сделки

Потребности, возникающие из финансовых операций самого казначейства.

### Financial Instrument / Финансовый инструмент

- **Суть.** Расчёты по финансовым инструментам (ценные бумаги, деривативы и т.п.).
- **Когда возникает.** При наступлении расчётной даты по сделке/инструменту.
- **Типовой объект/транзакция SAP.** Сделки TRM (Transaction Manager), расчётные потоки (flows).
- **Ключевые атрибуты.** Тип инструмента, контрагент, сумма, валюта, дата расчёта.
- **Связь с заявкой.** Расчётный поток по инструменту → потребность в оплате (`* → 1`).

### Loan / Заём

- **Суть.** Платежи по займам: выдача, погашение тела, проценты.
- **Когда возникает.** По графику обслуживания займа.
- **Типовой объект/транзакция SAP.** Сделки займа в TRM, расчётные потоки.
- **Ключевые атрибуты.** Контрагент, сумма, валюта, тип платежа (тело/проценты), дата.
- **Связь с заявкой.** Каждый платёж по займу → потребность в оплате (`* → 1`).

### Deposit / Депозит

- **Суть.** Платежи по депозитам: размещение средств, возврат, начисленные проценты.
- **Когда возникает.** При размещении/пролонгации/закрытии депозита.
- **Типовой объект/транзакция SAP.** Сделки депозита в TRM, расчётные потоки.
- **Ключевые атрибуты.** Контрагент (банк), сумма, валюта, срок, ставка, дата операции.
- **Связь с заявкой.** Операция по депозиту → потребность в оплате (`* → 1`).

## Treasury System (TRM) / Казначейская система

### Payment Request / Заявка на оплату (целевой объект)

- **Суть.** Единый управляемый объект казначейской системы, в который сходятся потребности
  из всех систем-источников. Точка входа в сквозной платёжный процесс.
- **Источник/вход.** Входящие потребности от любой из сущностей выше (MM/SD/FI/TRM).
- **Кардинальность.** Многие источники → одна заявка (`* → 1`): различные сущности порождают
  потребности, которые консолидируются/формализуются в объект заявки.
- **Взаимоисключаемость источника.** Одна конкретная входящая потребность порождается
  ровно одним источником (MM **или** SD/FI **или** FI **или** TRM). На уровне типа связь
  «многие → один», но каждая отдельная потребность имеет единственный источник-владелец.
- **Поведенческий стык со сквозным процессом.** Возникновение потребности и её
  формализация соответствуют последовательности шагов
  `Incoming Payment Request Demand → Generate Payment Request` основного процесса: сначала
  фиксируется потребность (пред-статус), затем формируется объект заявки со статусом
  `Created / Создан`.
- **Ключевые атрибуты.** Сумма, валюта, контрагент, срок оплаты (due date), источник
  (MM/SD/FI/TRM), документ-основание (ссылка на сущность-источник).
- **Связь со сквозным процессом.** Соответствует шагам
  `Incoming Payment Request Demand → Generate Payment Request` основного процесса
  (`Платёжный_процесс_полный.PlantUml`); после формирования объект получает статус
  `Created / Создан`.
- **Роль (RACI).** Заявитель / бизнес-подразделение — R/A (по инициации потребности);
  казначейство — обработка заявки в дальнейшем процессе.

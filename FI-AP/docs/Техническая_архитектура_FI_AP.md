# Техническая архитектура микросервиса FI-AP

## 1. Назначение

Документ фиксирует технологический стек и основные компоненты вспомогательного
микросервиса FI-AP.

Сервис предназначен для параллельной генерации открытых позиций кредиторов,
транзакционного создания событий Outbox и публикации `payment.demand` в Kafka.
Сервис запускается как одноразовое CLI-приложение и не предоставляет HTTP API.

Функциональные правила генерации описаны в документе
[`Генерация_открытых_позиций.md`](Генерация_открытых_позиций.md).

## 2. Технологический стек

| Компонент | Выбранная технология | Назначение |
|---|---|---|
| Язык | Go 1.27.0 | Реализация приложения. Используется последняя стабильная версия, зафиксированная для проекта. |
| Базовые компоненты | Стандартная библиотека Go | CLI, управление контекстом, конкурентное выполнение, завершение по системным сигналам и базовая работа с вводом-выводом. |
| СУБД | PostgreSQL | Хранение документов-оснований, открытых позиций, Outbox и истории попыток публикации. |
| Доступ к PostgreSQL | `pgx` | Пулы соединений, запросы и транзакции без дополнительного ORM. |
| Миграции | Goose | Версионирование и применение изменений схемы PostgreSQL. |
| Kafka-клиент | `franz-go` | Публикация событий `payment.demand` и получение подтверждения Kafka. |
| Управление зависимостями и сборка | Go Modules | Воспроизводимая сборка и фиксация версий зависимостей в `go.mod` и `go.sum`. |
| Конфигурация | YAML | Описание именованных сценариев генерации и справочных тестовых данных. |
| Журналирование | `log/slog`, формат JSON | Структурированные технические и бизнес-события приложения. |
| Метрики | Prometheus client for Go | Предоставление метрик генерации, Outbox и Kafka для последующей визуализации в Grafana. |
| Интеграционные тесты | Testcontainers for Go | Запуск изолированных PostgreSQL и Kafka в автоматических тестах. |

Дополнительный web-фреймворк не используется, поскольку сервис не содержит HTTP API.

## 3. Основные компоненты приложения

### 3.1. CLI

Принимает имя сценария через параметр `--scenario`, загружает YAML-конфигурацию,
проверяет параметры и запускает приложение.

### 3.2. Scenario Loader

Загружает выбранный сценарий и общие справочные данные. Выполняет структурную и
семантическую валидацию до создания данных.

### 3.3. Generation Coordinator

Координирует один запуск:

- создаёт уникальный `runId`;
- рассчитывает количество исходных документов;
- получает номера документов из `fi_document_number_seq`;
- формирует задания на создание позиций;
- запускает фиксированный пул генераторов;
- собирает результаты выполнения.

### 3.4. Position Generator

На основании сценария, `randomSeed` и номера задания формирует `OriginDocument`,
`OpenVendorItem` и содержимое события `payment.demand`.

### 3.5. Repository

Работает с PostgreSQL через `pgx`. В одной транзакции сохраняет:

```text
OriginDocument (если сформирован)
+ OpenVendorItem
+ Outbox
```

Repository не публикует данные непосредственно в Kafka.

### 3.6. Outbox Publisher

Выбирает подготовленные события Outbox, создаёт записи
`OutboxDeliveryAttempts`, публикует сообщения через `franz-go` и фиксирует результат
каждой попытки.

### 3.7. Observability

Формирует структурированные JSON-логи и метрики Prometheus. Все записи, относящиеся
к запуску генератора, содержат `runId`.

## 4. Конкурентная модель

Для генерации используется фиксированное количество goroutine, равное
`parallelThreads`. Задания передаются через канал. Один номер задания может быть
обработан только одной goroutine.

Отмена и штатное завершение распространяются через `context.Context`. Доступ к
PostgreSQL выполняется через общий безопасный для конкурентного использования пул
`pgx`.

Количество goroutine обработчика Outbox настраивается независимо от
`parallelThreads`. Детальная политика выборки, блокировки и повторной публикации
описывается отдельной спецификацией Outbox.

## 5. Управление схемой данных

Схема PostgreSQL управляется миграциями Goose. Миграциями создаются таблицы,
ограничения, индексы и sequence:

```text
fi_document_number_seq
```

Таблицы, типы колонок, ключи, проверки и индексы представлены на отдельной диаграмме
[`Физическая_модель_БД_FI_AP.PlantUml`](Физическая_модель_БД_FI_AP.PlantUml).

Значение `OpenVendorItem.documentNumber` получается только через:

```sql
nextval('fi_document_number_seq')
```

Расчёт номера через `MAX(documentNumber) + 1` запрещён из-за риска коллизий при
параллельной работе.

## 6. Границы ответственности

Приложение отвечает за:

- создание корректных тестовых данных;
- транзакционную целостность `OpenVendorItem` и `Outbox`;
- надёжную отправку событий в Kafka;
- журналирование и метрики;
- корректное завершение запуска.

Приложение не отвечает за бухгалтерские расчёты, пользовательский интерфейс,
управление корпоративными справочниками и обработку заявок в TRM.

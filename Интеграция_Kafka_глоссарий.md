# Глоссарий: интеграция источников с казначейской системой через Kafka

Справочник по элементам схемы `Интеграция_Kafka.PlantUml` (компонентная диаграмма
event-driven интеграции: продюсеры → топики Kafka → консьюмер в казначейской системе).

Схема показывает, **как настроена работа через Kafka**: кто публикует события потребности
в оплате, через какие топики и контракты они проходят и как потребляются казначейской
системой для формирования заявки на оплату.

Каждый элемент описывается по единой структуре: суть, роль в интеграции, ключевые
настройки/атрибуты, связи, риски.

---

## Продюсеры (Producers)

### MM / SD-FI / FI / TRM — Source Systems / Системы-источники

- **Суть.** Операционные системы/модули, в которых возникает потребность в оплате
  (см. `Источники_потребности_глоссарий.md`). В event-driven модели они выступают
  продюсерами событий.
- **Роль в интеграции.** Формируют бизнес-событие «возникла потребность в оплате» и
  передают его в слой публикации (Outbox).
- **Ключевые атрибуты.** Тип источника (MM/SD/FI/TRM), тип события, бизнес-ключ
  (контрагент/документ), полезная нагрузка (сумма, валюта, срок, основание).
- **Связи.** `--> Outbox / Event Publisher`.
- **Риски.** Потеря события при сбое, несогласованность бизнес-данных и события
  (решается паттерном Outbox — транзакционная запись события вместе с бизнес-операцией).

---

## Слой публикации

### Outbox / Event Publisher (Kafka Connect / SAP AIF) / Выгрузка событий

- **Суть.** Компонент, надёжно публикующий бизнес-события из систем-источников в Kafka.
  Реализует паттерн Outbox: событие сохраняется в БД в одной транзакции с бизнес-операцией,
  затем асинхронно публикуется в топик.
- **Роль в интеграции.** Развязывает источники и Kafka, гарантирует надёжную доставку
  (нет потери события при сбоях), выполняет маппинг во внешний контракт события.
- **Ключевые атрибуты/настройки.** Механизм чтения outbox (CDC/поллинг), сериализация
  (Avro/JSON), ключ партиционирования, повторные попытки публикации.
- **Связи.** `Producers --> Outbox`, `Outbox --> Topic payment.demand (produce)`,
  `Outbox ..> Schema Registry (register/validate)`.
- **Риски.** Дублирующая публикация (обрабатывается идемпотентностью на консьюмере),
  отставание outbox (лаг), рассинхрон схемы.

#### Зачем нужен паттерн Outbox (проблема dual-write)

Прямая публикация «записал в БД и сразу отправил в Kafka» ненадёжна: это два отдельных
ресурса без общей транзакции (проблема **dual-write**). Если после коммита в БД падает
отправка в Kafka (или наоборот) — данные и события рассинхронизируются: платёжная
потребность есть в системе, а события нет (или наоборот — дубль).

**Решение Outbox:** бизнес-операция и запись события в таблицу `outbox` выполняются в
**одной локальной транзакции БД**. Отдельный процесс затем читает `outbox` и публикует
события в Kafka. Это даёт гарантию **at-least-once** без распределённых транзакций.

#### Способы чтения outbox и публикации

- **CDC (Change Data Capture) через Debezium.** Коннектор читает журнал транзакций БД
  (redo/WAL) и стримит изменения таблицы `outbox` в Kafka. Наиболее популярный и
  «неинвазивный» способ; у Debezium есть готовый **Outbox Event Router** (SMT), который
  маршрутизирует записи outbox в нужные топики.
- **Polling Publisher.** Периодический опрос таблицы `outbox` (SELECT необработанных строк)
  и публикация. Проще, но создаёт нагрузку на БД и лаг опроса.
- **Kafka Connect.** Среда исполнения коннекторов (source/sink); Debezium работает как
  source-коннектор внутри Kafka Connect. Обеспечивает масштабирование, offset-tracking,
  рестарты.
- **SAP AIF (Application Interface Framework) / SAP Integration Suite.** В SAP-ландшафте
  выгрузка событий может идти через AIF (мониторинг/обработка интерфейсов) или через
  SAP Integration Suite / Advanced Event Mesh (managed-брокер, совместимый с Kafka).
  Альтернатива — SAP-source-коннекторы для Kafka Connect.

## Apache Kafka

### Topic: payment.demand / Топик потребности в оплате

- **Суть.** Основной канал событий о входящей потребности в оплате.
- **Роль в интеграции.** Буферизует и распределяет события между продюсерами и консьюмерами;
  обеспечивает масштабирование и упорядочивание.
- **Ключевые настройки/атрибуты.**
  - **Ключ сообщения** = контрагент/документ-источник (определяет партицию и порядок).
  - **Партиции** — параллелизм обработки; порядок гарантируется в пределах одной партиции.
  - **Retention** — срок хранения событий (для повторного проигрывания/восстановления).
  - **Репликация** — отказоустойчивость (replication factor).
- **Гарантии.** At-least-once доставка; порядок по ключу в пределах партиции.
- **Связи.** `Outbox --> Topic (produce)`, `Topic --> Demand Consumer (consume)`.
- **Риски.** Неудачный выбор ключа → «перекос» партиций (hot partition) и нарушение
  равномерности нагрузки; недостаточный retention → потеря возможности реплея.

### Topic: payment.demand.DLQ / Dead-Letter топик

- **Суть.** Топик для событий, которые не удалось обработать после исчерпания повторных попыток.
- **Роль в интеграции.** Изолирует «ядовитые»/ошибочные сообщения, чтобы не блокировать
  поток; служит для ручного/автоматического разбора.
- **Ключевые атрибуты.** Причина ошибки, исходный офсет/партиция, число попыток, оригинальный payload.
- **Связи.** `Demand Consumer --> DLQ (on error)`.
- **Риски.** Разрастание DLQ без мониторинга, потеря бизнес-события без разбора, отсутствие
  процесса реобработки.

### Schema Registry / Реестр схем

- **Суть.** Централизованный реестр контрактов событий (Avro/JSON Schema) с версионированием.
- **Роль в интеграции.** Гарантирует совместимость продюсеров и консьюмеров, контролирует
  эволюцию схем (backward/forward compatibility).
- **Ключевые атрибуты/настройки.** Subject/версия схемы, политика совместимости, формат сериализации.
- **Связи.** `Outbox ..> Schema Registry (register/validate)`,
  `Demand Consumer ..> Schema Registry (deserialize)`.
- **Риски.** Несовместимое изменение схемы ломает консьюмеров; отсутствие политики
  совместимости; рассинхрон версий.

## Консьюмер (Treasury System / TRM)

### Demand Consumer (consumer group: trm-demand) / Консьюмер потребности

- **Суть.** Компонент казначейской системы, подписанный на топик `payment.demand` и
  вычитывающий события.
- **Роль в интеграции.** Приём и десериализация событий, управление офсетами, маршрутизация
  в формирование заявки, обработка ошибок (ретраи/DLQ).
- **Ключевые настройки/атрибуты.**
  - **Consumer group** `trm-demand` — масштабирование: партиции распределяются между
    инстансами группы.
  - **Управление офсетами** (commit после успешной обработки).
  - **Политика ретраев** и порог отправки в DLQ.
- **Связи.** `Topic --> Demand Consumer (consume)`, `Consumer ..> Schema Registry`,
  `Consumer --> Payment Request Builder`, `Consumer --> DLQ (on error)`.
- **Риски.** Дубликаты при at-least-once (нужна идемпотентность), «застревание» на ядовитом
  сообщении, ребалансировка группы, коммит офсета до успешной обработки (потеря события).

### Payment Request Builder / Формирование заявки

- **Суть.** Логика преобразования события-потребности в объект `Payment Request` в TRM.
- **Роль в интеграции.** Маппинг полезной нагрузки события в атрибуты заявки, применение
  бизнес-правил, идемпотентная запись.
- **Ключевые атрибуты.** Правила маппинга, ключ идемпотентности (ключ события),
  валидация обязательных полей.
- **Связи.** `Demand Consumer --> Payment Request Builder`, `--> Payment Request (upsert)`.
- **Риски.** Некорректный маппинг, неидемпотентная запись (дубли заявок), потеря контекста
  источника.

### Payment Request / Заявка на оплату (целевой объект)

- **Суть.** Итоговый управляемый объект казначейской системы — результат интеграции;
  точка входа в сквозной платёжный процесс.
- **Роль в интеграции.** Единый объект, в который сходятся события из всех систем-источников.
- **Ключевые атрибуты.** Сумма, валюта, контрагент, срок оплаты, источник (MM/SD/FI/TRM),
  документ-основание, ключ события (для дедупликации).
- **Связи.** `Payment Request Builder --> Payment Request (upsert)`; далее — сквозной процесс
  (`Платёжный_процесс_полный.PlantUml`), статус `Created / Создан`.
- **Риски.** Дубли заявок при нарушении идемпотентности, рассинхрон с источником.

## Ключевые сквозные принципы интеграции

- **At-least-once + идемпотентность.** Kafka гарантирует доставку «хотя бы один раз»,
  поэтому дедупликация выполняется на консьюмере по ключу события.
- **Порядок по ключу.** Упорядочивание событий обеспечивается только в пределах партиции;
  ключ (контрагент/документ) выбирается так, чтобы связанные события шли по порядку.
- **Контракты через Schema Registry.** Изменения схем — только совместимые, с версионированием.
- **Изоляция ошибок через DLQ.** Ошибочные события не блокируют поток и подлежат разбору/реобработке.
- **Развязка систем.** Продюсеры и консьюмер независимы: источники не знают о TRM напрямую,
  взаимодействие идёт через топики.

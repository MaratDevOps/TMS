# Промпт: создание Git-коммитов

Используй этот промпт для подготовки и создания Git-коммитов в текущем репозитории.

## Основные правила

- Не изменяй настройки Git и данные автора.
- Автором коммита должен оставаться пользователь, указанный в локальной конфигурации Git.
- Не добавляй упоминания AI, агента или соавторства.
- Не выполняй `push`, если пользователь явно не попросил отправить коммиты.
- Не используй `--no-verify`, `--no-gpg-sign` и другие способы обхода проверок.
- Не включай файлы с секретами, токенами, паролями или локальными настройками окружения.

## Анализ изменений

Перед созданием коммита:

1. Выполни `git status`, чтобы увидеть изменённые, удалённые и новые файлы.
2. Изучи staged и unstaged diff.
3. Посмотри последние сообщения коммитов и соблюдай стиль репозитория.
4. Определи смысл каждого изменения и связи между файлами.
5. Проверь, нет ли в индексе ранее добавленных пользователем изменений.

Не коммить файлы, содержание которых не было проверено.

## Разделение на коммиты

- Один коммит должен описывать одно логически завершённое изменение.
- Разделяй независимые изменения на отдельные коммиты.
- Связанные изменения модели, контракта и маппинга можно объединить, если они реализуют
  одно решение и не имеют самостоятельной ценности по отдельности.
- Удаление устаревших файлов отделяй от функциональных или содержательных изменений.
- Изменение общих правил и шаблонов отделяй от изменений конкретной документации.
- Документацию, разработку и отдельное тестирование разделяй по фазам `.1`, `.2` и `.3`.
- Юнит-тесты не отделяй от кода функционала: они входят в `.2`.
- Не создавай искусственно мелкие коммиты для отдельных строк одного решения.
- Перед созданием нескольких коммитов сначала сообщи пользователю предлагаемое разделение.

## Фазы спринта

Префикс сообщения: `Sprint x.y`.

| Суффикс | Фаза | Что входит |
|---|---|---|
| `.1` | Написание документации | Спецификации, контракты, модели, промпты, правила |
| `.2` | Разработка | Код приложения, конфигурация, миграции схемы, юнит-тесты |
| `.3` | Тестирование | Отдельное тестирование: интеграционные и системные проверки, сценарии прогона, стенды |

Юнит-тесты создаёт разработчик вместе с функционалом. Это часть разработки (`.2`), а не фаза тестирования.
В `.3` попадают только проверки, которые не являются юнит-тестами кода функции: интеграция с внешними системами, сценарии прогона, стенды.

Номер спринта `x` берётся из текущей работы. Суффикс `y` — только из таблицы выше.
Если в рабочей директории есть изменения нескольких фаз, это отдельные коммиты.

## Сообщение коммита

Сообщение пишется на русском языке.

Требования:

- не использовать глаголы;
- описывать суть и результат изменения, а не имя изменённого файла;
- если изменение устраняет коллизию между требованиями, контрактами или моделями,
  отражать в сообщении согласование затронутых понятий и ограничений, а не механическое
  добавление, удаление или переименование отдельного реквизита;
- не повторять название файла, каталога или документа без пояснения смысла;
- избегать общих формулировок: «изменения», «обновление файлов», «правки»;
- использовать одно короткое предложение без точки в конце;
- начинать сообщение с префикса `Sprint x.y` по таблице фаз спринта;
- фазу выбирать по смыслу изменения, а не по номеру из соседних коммитов.

Плохие варианты:

```text
Обновление Промт_ER_диаграмма.md
Изменения документации
Исправить контракт
Добавить ER-диаграмму
Sprint 1.2: правки
```

Хорошие варианты:

```text
Sprint 1.1: единые правила проектирования ER-моделей
Sprint 1.1: идентификация документов в модели TRM
Sprint 1.1: контракт создания и актуализации заявок FI-AP
Sprint 1.2: CLI-генератор открытых позиций FI-AP
Sprint 1.3: интеграционная проверка публикации payment.demand
```

## Создание коммита

Для каждого логического коммита:

1. Добавь в индекс только относящиеся к нему файлы.
2. Проверь staged diff.
3. Создай коммит с согласованным сообщением.
4. Проверь результат через `git status` и `git log`.
5. Убедись, что автор коммита совпадает с локальной учётной записью пользователя.

Если команда была прервана, не предполагай, что она завершилась. Проверь фактическое
состояние индекса и последний коммит перед повторным запуском.

## Ограничения

- Не выполняй `git reset --hard`, принудительный push и другие разрушительные команды.
- Не исправляй чужой коммит через `--amend` без явного запроса пользователя.
- Не создавай пустые коммиты.
- Не включай в коммит посторонние незавершённые изменения.
- Не отправляй коммиты в удалённый репозиторий автоматически.

## Итоговый отчёт

После завершения сообщи:

- хеш и сообщение каждого созданного коммита;
- какие логические изменения вошли в каждый коммит;
- имя и email автора;
- состояние рабочей директории;
- выполнялся ли `push`.
